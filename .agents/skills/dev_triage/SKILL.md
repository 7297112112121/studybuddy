# 入口分流与小修改轨道（triage）

## 概述

开发入口的唯一闸门，两个职责：

- **分流**：判断开发请求走全量研发流程还是小修改轨道。全量流程是重装备——proposal、design、tasks 三道批准门是为特性级需求设计的；改一行文案、调一个按钮配色也背上它，成本远大于收益。分流的目的就是让小改动不背全流程的重量。
- **小修改轨道执行**：确认修改点 → 提出 2-4 个方案（理由 + 风险）→ 用户选定 → 落地（TDD 或非函数直改）→ 局部测试 → 提交，在本技能内闭环。

**开始时声明**：「我正在使用 dev_triage 技能<分流 / 以小修改轨道处理 <改动描述> >。」

## 流程前后继

上游：用户的开发请求，无前置工件。下游：小修改轨道——branch-wrapup（fix/feat 分支收束）；判定全量流程——product_design（产品侧起步）。

## 分流判断

按维度现场判断，不设死清单：

- **影响面**：单点局部改动 vs 跨模块联动（修一处动十处）；
- **行为变更**：文案/样式/局部交互微调 vs 对外行为、数据流向、鉴权与安全的变化；
- **结构性**：既有页面/组件内的小步演进 vs 新增整页、整特性、新接口、需要依赖选型；
- **装得下**：小修改轨道的步骤能否覆盖改动全程，不会中途长出结构决策。

倾向信号（供快速判断，非硬边界）：

- 走小修改轨道：改文案、调样式、微调 UI、修既有缺陷、加一个字段（含 Drizzle 迁移，落地前按 AGENTS.md 加载 drizzle 技能）、单一组件内的小功能；
- 回全量流程：新增整页/整特性、跨模块行为变更、鉴权/安全/数据流改向、需要新增接口或依赖选型、改动波及面明显超出单点。

**分流结论必须先声明再动手**——「我判定这走<小修改轨道/全量流程>，理由：<一句话>」。拿不准时列理由问用户，不擅自选全量流程吓退小改动，也不擅自选小修改轨道吞下特性级需求。

**中途升级**：小修改轨道执行中发现改动蔓延（要动的文件越改越多、出现结构性决策、需要新接口）——停手，已完成部分收口提交，回全量流程。装不下的就是计划。

## 小修改轨道流程

### 1. 确认修改点

用 codegraph 定位改动落点（文件、符号、行号），向用户复述确认：「要改的是 X，落点在 Y」。修改点含糊时先问清，不猜。同时确认这是不是用户要的唯一改动——隐性范围扩张在这一步拦住。

### 2. 方案与选定（HARD-GATE）

提出 2-4 个实现方案，每个含：做法、理由、风险。**用户选定前不得写任何产品代码**。用户请求里已带明确方案时，改为确认 + 至少给一个备选视角，而非机械重提。涉及数据、鉴权的方案无论多小都必须等确认。

### 3. 落地

- **函数/逻辑改动**：TDD——先写失败测试（只测改动点）→ 运行确认红 → 最小实现 → 确认绿。测试跟着改动走，不在现场搭测试基建。
- **样式/UI 等非函数改动**：跳过 TDD，默认编程方式直改。
- 最小改动原则：不顺手重构、不夹带；顺手想改的单独提出，由开发者决定。

### 4. 测试约束（HARD-GATE）

**禁止全量单测、禁止 e2e**。只跑修改所在文件/目录的相关测试 + `npm run lint`。全量回归是全量流程的收口动作（dev_implementation 硬门禁管的是那条轨道）；小修改轨道用局部绿换速度，这是有意取舍，不是偷懒——覆盖缺口由 lint 与改动范围小来兜底。

### 5. 提交与收束

Conventional Commits 中文描述（fix:/feat:/style:/chore: 按改动性质取型）。完工触发 branch-wrapup 收束 fix/feat 分支；合并须等用户确认，未表态不得自行合并。

## 触发范围

**不触发**：纯文档改动（doc_writing）、studybuddyui 草稿区条目（component-*/layout-* 家族）、一次性脚本、纯提问/调研不落码、spike 原型验证。

## 合理化对照表

| 借口                                     | 现实                                                              |
| ---------------------------------------- | ----------------------------------------------------------------- |
| 「这么小还分什么流，直接改了」           | 分流结论不声明，用户就不知道这次改动背了多少流程成本               |
| 「方案显然只有一种，不用选了」           | 至少给一个备选视角；选定门防的是盲区，不是效率                     |
| 「顺手把旁边的也修了」                   | 最小改动原则；顺手改动单独提出，由开发者决定                       |
| 「局部绿不放心，跑个全量保险」           | 全量与 e2e 是全量流程的收口动作；小修改轨道明确禁止                |
| 「UI 改动也要先写测试」                  | 非函数改动跳过 TDD，直改即可                                       |
| 「改着改着变大了，继续做完吧」           | 改动蔓延即停手回全量流程，装不下的就是计划                         |
| 「小修改不用开分支，直接改 master」      | 收束走 branch-wrapup，分支模型不因改动小而豁免                     |

## 产出物

- 产品代码与测试（局部）
- Conventional Commits 中文提交
- 无 proposal/design/tasks 工件；分流存在争议时，在回复中记录判断理由供用户复核
