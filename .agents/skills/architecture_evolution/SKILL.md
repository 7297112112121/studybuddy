# 系统架构演进（architecture_evolution）

## 概述

横切的全局层技能，不在特性研发单向流内：从全局视角评审软件系统——代码目录、依赖方向、数据流向、技术资产——产出裁决并回写既有真源，应对业务增长与架构滞后的偏差。单特性设计（dev_architecture_design）把 `docs/dev/代码目录.md` 当封闭清单消费，装不下就登记开放问题；本技能是维护这份清单与相关真源的一方，两者由此互为上下游。

**设计原则**（每个风险主张与裁决以此检验）：

- **证据先行**：每个风险主张附代码证据（文件、符号、调用路径）；图与代码对照后下结论，不凭感觉评审。
- **只设计足够当前需求的架构**：裁决只覆盖当下有证据的问题；不为假想需求预留抽象层、占位目录、可选扩展点。
- **模糊不具体，延迟决策**：证据不足或影响面说不清的问题不裁决，登记观察项（触发条件 + 复查时机），证据到位再入裁决。
- **不搞酷炫架构**：评审轴心是易维护、可读性强；拒绝炫技式分层、过早的通用化与为模式而模式。

**开始时声明**：「我正在使用 architecture_evolution 技能对系统整体架构做评审与演进。」

## 何时使用 / 不使用

**使用**：

- 显式请求：架构评审、架构演进、目录结构审视、依赖方向治理、技术资产盘点；
- 结构性阻塞回流：dev_architecture_design 盘点落点时发现清单装不下不止一处、需变更模块形状或数据流向——超出单特性可裁定范围的问题。

**不使用**：

- 单特性架构设计（proposal → design）——dev_architecture_design；
- 引入新库 / 框架 / 服务的选型——adr_writing（本技能的裁决需要新选型支撑时，同样移交）；
- 产品需求澄清——product_design；
- 按既定计划重构实施——dev_plan_writing / dev_implementation。

## 硬门禁（HARD-GATE）

1. **评审方案未获人工批准，不得回写任何真源。** `docs/dev/代码目录.md`、ADR、既有技能文档在被批准前保持原样；摘要以「草案」状态落盘。
2. **关键裁决不由 AI 单方拍板。** 目录增删、数据流向变更、依赖规则变更，逐项给候选供开发者选择；AI 只摆证据与选项，不做最终裁定。
3. **只裁决，不实施。** 本技能不写产品代码；裁决对应的重构另起 feat/AXY 流程落地。

## 分支衔接

**流程前后继**：上游——显式请求（无前置工件），或 dev_architecture_design 的结构性阻塞回流；下游——真源回写（代码目录.md）、adr_writing（选型裁决落 ADR）、上游开放问题闭环通知。

评审在 `docs/arch-<slug>` 分支上进行：不在对应分支时，从最新 `master` 新建（slug 描述本次评审主题）；侦察、裁决、摘要落盘、批准、真源回写全部在该分支上完成，收尾走 branch-wrapup。

## 流程

### 1. 侦察盘点

先读真源与背景，再对照实际代码：

- 读 `docs/dev/代码目录.md` 全景（目录树、路由、业务模块、数据流向）与 `docs/dev/adr/index.md` 的决策日志和现行技术栈速查；
- 读评审背景：显式请求的开发者关注点，或回流特性登记的开放问题原文；
- 用 codegraph 与实际文件对照真源：目录清单与 `src/` 实际形状、ADR 速查与 `package.json` 实际依赖、数据流向图与真实调用路径。**不问项目与文档已回答的问题，不重开已决定的事项。**

批量证据收集可派子代理并行（prompt 必须自包含：查什么、返回什么格式）；裁决对话与最终裁定永远由主会话完成。

### 2. 风险识别

沿五个维度逐项列风险，每项一条：风险陈述 + 代码证据 + 影响面（现在痛在哪，不痛不列）。

| 维度     | 查什么                                                                             |
| -------- | ---------------------------------------------------------------------------------- |
| 依赖方向 | 模块间引用是否违反单向依赖与分层；循环依赖；绕过模块唯一入口（actions / queries）直连底层 |
| 模块形状 | 模块内部是否偏离统一形状（展示 / 编排 / 逻辑 / 数据四层）；文件职责漂移             |
| 真源漂移 | 代码目录.md 图示与 `src/` 实际不符；ADR 速查与实际依赖不符；死依赖、幽灵目录         |
| 数据流向 | 读写路径是否仍走唯一入口；状态归属是否漂移（store 承载服务端数据等）                |
| 技术资产 | 既有组件 / 工具函数被绕开重复造轮子；ADR 覆盖之外自生长的技术点                     |

### 3. 裁决对话

风险逐项过三类处置，与开发者逐项收敛：

- **裁决**：证据充分且影响明确——给 2-4 个候选，每个含方案一句话、理由（对照易维护与可读性）、风险（没有风险陈述的选型是推销）；开发者选定后记入裁决记录。
- **观察**：模糊不具体的、证据不足的——不裁决，登记观察项：触发条件（什么信号出现时必须回头处理）+ 复查时机。
- **移交**：裁决需要新选型支撑的——移交 adr_writing 走 ADR 流程，结论回来后继续。

一次一项；候选数量服务于选择权，不为凑数造选项。

### 4. 落评审摘要

写入 `docs/dev/arch-review/<slug>.md`，一页纸以内：头部状态行（草案 → 已批准）、评审范围与触发背景、风险清单（证据指针）、裁决记录（候选 / 理由 / 风险 / 裁定）、观察项（触发条件 + 复查时机）、真源回写清单（真源文件 + 目标节）。批准状态真源只在摘要头部表。

### 5. 提请批准

逐项核对：每条风险有代码证据；每项裁决经开发者选择且有风险陈述；观察项有触发条件；真源回写清单完整（改哪份真源、改哪一节）。通过后提请人工批准；**批准覆盖文档当前内容，其后改动须重新确认。**

### 6. 回写真源与下游衔接

批准后执行回写清单：

- `docs/dev/代码目录.md`：按四节全图纪律更新对应图示；
- 选型裁决：走 adr_writing 落 ADR 并登记索引；
- 回流来源的开放问题：通知对应特性的 design 按裁决闭合；
- 本技能不直接修改 `src/`；重构实施另走 feat/AXY 流程。

## 反模式对照表

| 借口                                    | 现实                                                                              |
| --------------------------------------- | --------------------------------------------------------------------------------- |
| 「为以后的多租户 / 插件化先留个抽象层」 | 假想需求没有证据。观察项登记触发条件，信号出现再裁决                               |
| 「这个方向感觉乱了，先定个规范」        | 感觉不是证据。先收集调用路径与引用事实，风险列不出来就不裁决                        |
| 「顺手把分层重构了，反正都评审到这了」  | 只裁决不实施。重构是 feat 流程的事，混进来评审范围与批准对象都会失控                |
| 「图和代码差一点，先不管」              | 真源漂移会让下游设计建立在错误地图上。漂移本身就是要回写的风险                      |
| 「一次把所有目录都重排个干净」          | 大爆炸式重排风险与返工最大。一次评审聚焦有证据的问题，没痛的不动                    |
| 「评审摘要先记着，真源等以后一起改」    | 批准门的意义就是批准后立即回写。拖着不回写，真源继续漂移                            |
| 「选型 obvious 对，候选不用摆了」       | 没摆上桌的选项等于没被考虑过；开发者要的是选择权                                    |

## 产出物

- `docs/dev/arch-review/<slug>.md` — 评审摘要（状态：草案 → 已批准；含风险清单、裁决记录、观察项、回写清单）
- `docs/dev/代码目录.md` — 批准后的真源回写（图示更新）
- ADR（经 adr_writing 衔接）— 选型类裁决的决策记录
- 上游特性 design 的开放问题闭环通知（回流场景）
