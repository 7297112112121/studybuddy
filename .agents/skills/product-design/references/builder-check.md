# Builder Check（builder-check）

移植自 obra/superpowers 的 builder check 机制。解决的问题：**AI 写的故事文档自己看得懂，因为上下文全在对话里；换一个执行者就会卡壳。** 用一个没读过对话的子代理审计文档，暴露「只有写文档的人才知道」的隐含假设。

## 时机

故事文档落盘后、提请批准前。**每次落盘都跑**——包括对存量故事按新模板补写之后。

## 操作

派一个**全新子代理**（无对话上下文），输入只有：

1. 故事文档全文；
2. 项目级公共文档（按 `.agents/skills/README.md`「流程接力约定」允许的最小集：文档地图、dod、依赖故事的 AC）。

**不给对话历史、不给侦察笔记、不给任何口头补充**——它模拟的就是「只拿到文档的下游」。

子代理 prompt（可整段复制）：

```text
你是一名即将实现该用户故事的建造者。只依据给定的材料工作，不得询问写文档的人。

通读材料后，报告你在开工前仍需要答案的问题。只报这一类：
- 你必须靠猜测才能继续，且猜错会改变实现方案的点。

以下不算缺口，不要报：
- 能从材料中直接推出的内容；
- 纯实现细节（怎么写代码、用什么库），建造者可自行裁定。

若没有重要缺口，只回答：「没有重要缺口」。
```

## 三堆处置

收到子代理回报的问题后，分三堆处理：

| 堆 | 判定 | 处置 |
| --- | --- | --- |
| 已答 | 对话或项目材料其实已回答 | 把答案**补进故事文档**（它本该在场） |
| 可裁定 | 建造者或 AI 能自行定夺、且不影响方案形状 | AI 定夺，文档内标注「AI 裁定 + 理由」 |
| 必须人答 | 只有提出者能答，且答案改变被建之物 | 汇总后向提出者提问 |

「必须人答」堆的纪律：

- **只此一轮**，按重要性从高到低排列，一次问完；
- 问完后把答案落进文档；仍未定的登记「开放问题」并注明影响；
- 禁止用 Builder Check 重开已决定的事项——那是对侦察阶段的失职。

## 通过标准

满足其一即通过：

1. 子代理回报「没有重要缺口」；
2. 回报的缺口已全部处置：已答堆补进文档、可裁定堆标注留痕、必须人答堆已获答案或已入开放问题。

未通过则修订文档后**再跑一次**（子代理须重新派全新实例，不沿用旧上下文）。

## 禁止事项

- 把 Builder Check 当评审装饰、跑完不改文档；
- 向子代理泄露对话上下文「帮它理解」——那会废掉检查本身；
- 用它替代 DOR 自检或人工批准门——三者各管一段：Builder Check 管可实施性，DOR 管就绪度，批准门管业务决定。
