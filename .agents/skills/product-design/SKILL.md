# 产品设计（product-design）

## 概述

产品技能组的唯一技能，负责研发流程第一部分「产品设计」：把一个模糊的想法澄清为**落盘的用户故事**。故事文档是产品阶段唯一入库资产，内含**原型契约**——原型的纯文本接口。开发落地（proposal → design → plan → 代码）以已批准的故事为前置输入。

**开始时声明**：「我正在使用 product-design 技能将这个想法转化为用户故事。」

## 何时使用 / 不使用

**使用**：用户提出的是未经结构化的想法——一句话需求、一个痛点、一个功能愿望，尚未形成用户故事。

**不使用**：
- 用户故事已存在于 docs/product——直接进入 proposal-writing；
- 想法属于纯技术决策（选库、目录结构等）——走 ADR 流程；
- 对既有用户故事的修订——直接编辑对应文档，但若修订触及验收标准，须同步通知下游 proposal 持有者。

## 硬门禁（HARD-GATE）

1. **用户故事未经人工批准，不得进入开发落地。** proposal-writing 以「已批准的用户故事」为输入前提；未批准的故事状态标记为「草案」。
2. **原型一律不入库。** 任何交互原型（含 spike 演示）不提交进仓库；入库资产只有故事文档及其原型契约。需要看效果时按契约现场生成一次性原型，看完即弃。
3. **AXY 编号由项目管理平台生成。** 技能与 AI 不得自行分配、顺延或复用编号。新故事先产出名单（名称 + 一句话内容 + 依赖）向提出者申请编号，取号后回填文档与索引。
4. **单故事迭代。** 一次只澄清与落盘一个故事；发现多个独立故事时先切割、逐个处理，禁止批量产出。

## 流程

### 1. 侦察

读 docs/product/index.mdx 用户故事索引、相邻故事与 docs/intro.md，盘点既有领域实现。**不问项目与文档已回答的问题，不重开已决定的事项。** 证据收集可派子代理并行（prompt 必须自包含：写明查什么、返回什么格式），环境不支持时内联执行并明说；向提出者的提问与最终裁决永远由主会话完成，不委派。

### 2. 澄清对话

按 [references/questioning.md](references/questioning.md) 的协议进行：先开放题探 why，后选项式收敛；一次一问；每问必须改变产物；分段回放；归属标注。方向错误的成本远大于提问的成本——3000 token 的澄清对话能避免 500 行代码的方向性返工。

领域模型初识在对话中完成（借鉴 DDD 但不照搬，四问）：**概念与状态**（含界面可能隐藏的变体）、**状态的义务**（没人须行动的状态不是队列）、**动作的事件**（用领域语言表述）、**负空间**（业务刻意不设哪些概念——缺失本身是最贵的发现）。领域语言纪律：说不出业务含义、只能说实现方式的事实不进模型。

**界面字段 ↔ 模型属性双向核对**：每个界面字段都要能落到模型属性；落不到的在契约文本标 `[NEW]` 并登记「开放问题」，不得静默略过。

### 3. 边界确认与 MVP 切割

对话收口前与提出者确认三元组并写入故事：**目标 / 非目标 / 反目标**（反目标 = 技术上成功但产品上失败的路径）。

范围用三桶表述（借鉴 lobehub）：✅ 已建模已暴露 / ⚠️ 已建模未暴露 / ❌ 业务尚无此概念。❌ 项必须点名并写 cost drivers，禁止静默丢弃。

**MVP 切割判据**（全部满足才是一个故事）：

| 判据 | 标准 |
| --- | --- |
| 单演示主线 | 一个用户目标闭环，一条走查路径 |
| 演示态 | ≤ 5 |
| 验收标准 | AC ≤ 6；6–8 须在文档登记豁免理由；> 8 必拆 |
| 独立可演示 | 不依赖另一故事的演示态即可走查本故事全部 AC |

超限即拆：拆分只产出名单（名称 + 一句话 + 依赖）向提出者申请新编号（见硬门禁 3），拆分结论登记进索引与各故事「依赖与引用」。

### 4. （可选）spike 一次性原型

争议交互或说不清的体验，可做一次性单文件 HTML 给提出者看（规范见 [references/prototype-contract.md](references/prototype-contract.md) 的「spike 一次性原型」节）：看完即弃、不入库；有价值的结论回灌对话与故事文档；**产物转正视为新请求，重新过批准门**。

### 5. 落盘故事

按 [templates/user-story.md](templates/user-story.md) 写入 `docs/product/<feature>.mdx`，并在 `docs/product/index.mdx` 索引表登记一行：

- **目标 / 非目标 / 反目标、三桶范围、原型契约为必填节**；AC 每条行尾标注走查方式（〔走查：演示态 N〕或〔走查：行为说明 N〕）；
- 负空间结论落三桶 ❌；待定稿项与 `[NEW]` 字段登记「开放问题」；
- **DoD 不复制样板**：唯一真源是 `docs/product/dod.mdx`，故事文档只登记「工作项（本故事特有）」；
- 编号未下发时以「待编号」暂存标题，取号后回填（见硬门禁 3）。

原型契约按 [references/prototype-contract.md](references/prototype-contract.md) 撰写到**可构建级**：没读过对话的 AI 凭契约与项目文档，能做出可演示的实现。

### 6. Builder Check

落盘后、提请批准前，派**无上下文子代理**审计（操作与判定见 [references/builder-check.md](references/builder-check.md)）：只报「会改变方案的猜测点」，分三堆处置，仅一轮提问。通过标准：子代理回报无重要缺口，或缺口全部已进入开放问题。

### 7. DOR 自检与提请批准

逐项核对 DOR：故事清晰、验收标准可测试、粒度单 Sprint 可完成、依赖已识别、设计输入就绪。**DOR 是流程动作，不落盘成表**：自检结论记入文档头部状态行，缺口登记「开放问题」。全部通过后向提出者请求批准；批准后状态行改为「已批准」并附日期。**批准覆盖文档当前内容：其后再改须重新确认。**

## 反模式对照表

| 借口 | 现实 |
| --- | --- |
| 「先甩一版选项菜单让用户挑」 | 选项会锁死想象。why 未明只用开放题，让提出者自己描述 |
| 「我先填个合理默认值」 | 默认值必须说出口。没听过的默认无法被否决 |
| 「想法够清楚了，直接写故事」 | 你觉得清楚 ≠ 提出者觉得清楚。未提问产出的故事，AC 是猜的 |
| 「边界后面再定」 | 没有明确「不做什么」的故事，proposal 无法划定非目标，实现必然蔓延 |
| 「原型先做出来看看再说」 | 批准门前只允许 spike 且不入库；故事没批准就做原型 = 过度提早设计 |
| 「spike 能跑，直接在它上面继续做」 | spike 转正是新请求，回批准门重来 |
| 「Builder Check 问出一堆问题，再追问几轮」 | 只有一轮。问不完的进开放问题，不影响批准 |
| 「这几个故事类似，一批写完快」 | 批量产出 = 整页原型再切 AC 的老路。一次一个故事，逐个过 Builder Check |
| 「DOR 差一项也先开工」 | 差一项就不是就绪。要么补齐，要么把缺口写进开放问题并由提出者确认 |

## 产出物

- `docs/product/<feature>.mdx` — 用户故事（含 AC、三桶范围、原型契约、开放问题）
- `docs/product/index.mdx` — 用户故事索引表新增一行（编号来自项目管理平台）
- （临时）spike 一次性 HTML — 不入库，看完即弃
