# 产品设计（product-design）

## 概述

产品技能组的唯一技能，负责研发流程第一部分「产品设计」：把一个模糊的想法澄清为**落盘的用户故事**。开发落地（proposal → design → plan → 代码）以本技能的产出为前置输入。

**开始时声明**：「我正在使用 product-design 技能将这个想法转化为用户故事。」

## 何时使用 / 不使用

**使用**：用户提出的是未经结构化的想法——一句话需求、一个痛点、一个功能愿望，尚未形成用户故事。

**不使用**：
- 用户故事已存在于 docs/product——直接进入 proposal-writing；
- 想法属于纯技术决策（选库、目录结构等）——走 ADR 流程；
- 对既有用户故事的修订——直接编辑对应文档，但若修订触及验收标准，须同步通知下游 proposal 持有者。

## 硬门禁（HARD-GATE）

**用户故事未经人工批准，不得进入开发落地。** proposal-writing 以「已批准的用户故事」为输入前提；本技能产出的用户故事在获得批准前，状态标记为「草案」。

## 流程

### 1. 澄清（苏格拉底式提问）

在写任何东西之前先问，不要开始产出。围绕五类问题向提出者确认，每轮 3–5 个问题，逐轮收敛：

1. **角色与场景**：谁在什么处境下需要它？现有方式是怎么做的、痛在哪？
2. **目标与价值**：做成之后使用者得到什么？怎么判断它做成了？
3. **边界**：哪些明显不做？最小可用版本包含什么？
4. **依赖**：依赖哪些已有故事（参见 docs/product 线框图索引）？被谁依赖？
5. **数据口径**：涉及哪些实体与字段？状态如何流转？

**方向错误的成本远大于提问的成本。** 3000 token 的澄清对话能避免 500 行代码的方向性返工。

### 2. 领域模型初识

借鉴 DDD 但不照搬：识别概念、状态与流转即可，不强制分层战术模式。围绕四问建立初识模型（借鉴 lobehub product-design 的业务模型落地清单，绿地版）：

1. **概念与状态**：涉及哪些概念、角色与状态？含界面可能隐藏的变体；
2. **状态的义务**：每个状态迫使谁做什么？没人须行动的状态不是队列，有人被阻塞的状态才是急件；
3. **动作的事件**：每个动作让业务发生什么？用领域语言表述（「重新派单」而非「更新 status 字段」）；
4. **负空间**：业务刻意不设哪些概念？缺失本身是发现，且是最贵的那种——这些结论直接喂给 proposal 的非目标表。

**领域语言纪律**：模型口径用业务语言表述——说不出业务含义、只能说出实现方式（表结构、组件、字段类型）的事实不进模型。类型与约束由架构设计定稿，此处只回答「有哪些概念、叫什么、口径是什么」。

**界面字段 ↔ 模型属性双向核对**：界面先行时，每个界面上的字段都要能落到模型属性上。落不到的，在**线框图本体上**打 `NEW` 标记（可见的债，如数值旁标注 `[NEW] 待模型支持`），并登记进「开放问题」表——不得静默略过，也不得为求整洁从原型上移除标记。

### 3. 落盘用户故事

按 [templates/user-story.md](templates/user-story.md) 的结构写入 `docs/product/<feature>.mdx`，**沿用 docs/product 既有文档的格式**（故事主干 + 给定/当/则验收标准表 + 范围界定表 + 就绪定义 DOR 表 + 完成定义 DoD 表），并在 `docs/product/index.mdx` 的线框图索引表登记一行。范围界定表以步骤 2 的初识模型为依据：本故事需要但未建模的概念进 ❌ 行，负空间结论（刻意不设的概念）进「不纳入范围」。DoD 按研发流程三大部分划分：团队表分「必须完成」（开发落地交付门槛，固定样板逐字沿用）与「可选完成」（测试提质阶段，承接 proposal 豁免清单，不阻塞发布）两段；「工作项（本故事特有）」表写通用阶段装不下的专属完成标准（数据一致性、安全底线、占位标记约定等），标注所属阶段。

线框图（React 化交互原型）照既有样板的组件结构编写，置于 `website/src/components/wireframe/` 下、文档内 import 嵌入。低保真即可，重点是状态与交互可操作。落不到模型属性的字段在线框图上保留显式 `NEW` 标记。

### 4. 就绪自检与提请批准

逐项核对 DOR：故事清晰、验收标准可测试、粒度单 Sprint 可完成、依赖已识别、设计输入就绪。全部 ✅ 后向提出者请求批准；批准后状态改为「已批准」。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「想法够清楚了，直接写故事」 | 你觉得清楚 ≠ 提出者觉得清楚。未提问产出的故事，验收标准是猜的 |
| 「边界后面再定」 | 没有明确「不做什么」的故事，proposal 无法划定非目标，实现必然蔓延 |
| 「这字段怎么落库以后再说」 | 可以进开放问题并在线框图上打 NEW 标记，但必须显式记录；静默略过 = 给下游埋雷 |
| 「DOR 差一项也先开工」 | 差一项就不是就绪。要么补齐，要么把缺口写进开放问题并由提出者确认 |

## 产出物

- `docs/product/<feature>.mdx` — 用户故事（含验收标准、DOR）
- `website/src/components/wireframe/Us<N><Feature>Wireframe.tsx` — 交互原型
- `docs/product/index.mdx` — 线框图索引表新增一行
