# 需求规范编写（product_proposal_writing）

## 概述

产品技能组的第二技能，负责「产品设计」部分的后半步：把已批准的用户故事转写为一份**需求规范（proposal）**——回答做什么、不做什么、做到什么程度、边界在哪，并承载**原型契约**（原型的唯一入库资产与 AI 唯一接口）。用户故事只装五大组成部分，其余规范内容全部由 proposal 承接。后续的架构设计（dev_architecture_design）与实现计划（dev_plan_writing）都以 proposal 为准绳；终审（dev_spec_review）逐条核对的对象也是它。

**迭代粒度：一份 proposal 对应一个特性。** 多个特性混入一份 proposal 会让规范变成大杂烩，禁止。

**开始时声明**：「我正在使用 product_proposal_writing 技能为 <特性名> 编写需求规范。」

## 硬门禁（HARD-GATE）

**proposal 未获人工批准，不得开始架构设计、任务拆分，不得写任何产品代码。**

## 流程

### 0. 定位输入（按编号查索引）

编号即路径：故事文档位于 `docs/product/AXY-<N>-<slug>/story.md`（目录已由 product_design 在编号回填时创建），可对照 `docs/product/index.md` 总览核对状态。**目录不存在 = 编号未下发 = 故事未就绪**，视为故事不存在，不得触发本技能，也不得盲猜搜索文件。状态非「已批准」时同样不得触发。

### 1. 读取用户故事（含引用物）

打开用户故事全文（故事很短，只有五大组成部分），并**沿「依赖」回溯一层**：依赖故事的验收标准；更深的引用物按需再读。多条依赖线相互独立时可派子代理并行回溯——prompt 必须自包含（写明读哪个文件、摘取什么、返回格式），环境不支持子代理时内联执行并明说。proposal 的需求条目必须能追溯到用户故事的 AC，不得凭空新增需求，也不得静默丢弃任何一条 AC。

### 2. 范围澄清与领域建模

故事没说的规范内容，在本阶段向提出者确认后落盘，不得留白：

- **非目标**：用户故事没说不做的，逐项确认后写进「非目标」表；
- **领域建模**（借鉴 DDD 但不照搬，四问，每问产出一张表，落 proposal「领域模型」节）：**概念与状态**（概念与状态表：实体 / 属性 / 状态 / 状态流转，含界面可能隐藏的变体）、**状态的义务**（状态义务表：状态 → 谁须行动 → 义务 → 关联 R 或路由行为编号；没人须行动的状态不是队列）、**动作的事件**（领域事件表：事件用领域语言表述 → 触发 → 结果 → 关联 R）、**负空间**（负空间表：业务刻意不设的概念 → 理由 → 决策 ID 或非目标编号——缺失本身是最贵的发现）。领域语言纪律：说不出业务含义、只能说实现方式的事实不进模型；
- **界面字段 ↔ 模型属性双向核对**（写契约时执行，核对表落「领域模型」节）：每个界面字段标注 F 编号与所落模型属性；落不到的在核对表与契约文本标 `[NEW]` 并登记「开放问题」，不得静默略过。

### 3. 转写为需求规范

按 [templates/proposal.md](templates/proposal.md) 写入 `docs/product/AXY-<N>-<slug>/proposal.md`——目录已由 product_design 在编号回填时创建（不存在即第 0 步的前置信号，不得自行建目录），本文件是该特性需求规范的唯一落点；开发落地工件（design / tasks / review）落在 `docs/dev/AXY-<N>-<slug>/`。核心动作：

- **决策集中**：澄清对话与批准过程中的每项裁定（提出者 / PO / AI）登记进「关键决策记录」（D-01、D-02…），正文只引用决策 ID，不夹带长括号说明；已批准决策不得被后续转写静默推翻；
- **做什么**：把每条 AC 转化为编号的需求条目（R1、R2…，增强表含优先级 / 类型 / 需求 / 来源 / 验收断言 / 测试层 / 演示态 / 状态），表述可测试——终审时每条须有对应实现与测试证据；
- **单一事实源表**：字段与校验规则（F-xx）、错误文案（E-xx）、路由行为表——正则、规则、文案、守卫与跳转行为只在对应表定义一次，R 条目、边界与原型契约一律引用编号；
- **领域模型独立成节**：第 2 步四问的产出物（概念与状态 / 状态义务 / 领域事件 / 负空间）与界面字段 ↔ 模型属性核对表在 proposal「领域模型」节成表呈现，不塞进「依赖与影响」单元格；正文引用实体与状态时与该节口径一致；
- **验收矩阵**：AC ↔ R 双向覆盖核对；DOD / DOR / WF 等无 AC 来源的条目单列，不得漏登；
- **不做什么**：显式写出非目标（含第 2 步确认的项）；
- **性能与质量要求**：逐条列出可度量的指标与度量方式，验收归属标注「后置，非本期验收」；本节条目（Q）由测试提质阶段验收，dev_spec_review 终审不核对；
- **边界与约束**：输入的合法范围、异常情形、与既有特性的交互（规则细节引用 F 编号，不重复正则）；
- **开放问题**：逐项写明是否阻塞与阻塞条件；
- **待确认 / 冲突清单**：转写中发现的冲突与不一致登记为 C-xx 并给出建议处理方式，不得静默改写；
- **Changelog**：修订记录独立成节，正文只保留当前有效状态。

### 4. 原型契约

按 [references/prototype-contract.md](references/prototype-contract.md) 在 proposal 的「原型契约」节写到**可构建级**：没读过澄清对话的 AI 凭契约与项目公共文档，能做出可演示的实现。**契约瘦身**：只承载入口、布局块、视觉/交互状态与不可从 R 推导的 UI 细节，交互逻辑一律回引 R / F / E 编号，不复述验收标准。演示态对应用户故事的 AC 编号，双向贯通由验收矩阵承载：每条 AC 有覆盖（演示态 / 路由行为 / R 条目）、每个演示态挂 ≥ 1 条 AC、界面元素不属于演示态即从界面移除——禁止面向用户的占位入口（禁用按钮、死链接、『敬请期待』类）。交互原型不入库；需要看效果时按契约现场生成一次性 HTML，看完即弃。

### 5. 自查并提请批准

自查清单：

- [ ] 用户故事的每条 AC 都有对应需求条目（或已列入开放问题）
- [ ] 每条需求条目可测试、无歧义表述（「适当」「合理」之类的词已消灭）
- [ ] 非目标已确认，不含糊
- [ ] 原型契约双向贯通无遗漏，体量 ≤ 150 行
- [ ] 无占位入口：界面不呈现任何范围排除项的假入口
- [ ] 性能与质量要求逐条可度量（验收归属已写明：测试提质阶段）
- [ ] 开放问题已列出且不阻塞核心路径
- [ ] 错误文案只在 E 表定义一次，R 条目与契约只引用 E 编号
- [ ] 校验规则只在 F 表定义一次，其他位置引用 F 编号
- [ ] 路由守卫与跳转行为只在路由行为表定义一次
- [ ] 所有裁定已归入 D 表，正文不夹带长括号说明
- [ ] 领域模型四问（概念与状态 / 状态义务 / 领域事件 / 负空间）已完成，每问有表可查
- [ ] 界面字段全部落到模型属性，或已标 `[NEW]` 并登记开放问题；术语表覆盖正文使用的全部领域名词
- [ ] 冲突与不确定项已进入「待确认 / 冲突清单」，未静默改写
- [ ] 修订进 Changelog，正文只保留当前有效状态

自查通过后提请人工批准。批准前状态为「草案」，批准后改为「已批准」并附批准日期。**批准通过即产品侧完工：触发 branch-wrapup 技能，把 docs 分支 PR 合并回 master**——开发侧（dev_architecture_design）在 proposal 进入 master 后才开工。

## 分支衔接

**流程前后继**：上游——product_design（已批准用户故事）；下游——dev_architecture_design（proposal 经 branch-wrapup 合并进 `master` 后承接）。

proposal 在 product_design 开出的 `docs/<slug>` 分支上编写与修订，不另开分支。生命周期真源见 [README](../README.md)「总流程与分支生命周期」。

## 合理化对照表

| 借口                                             | 现实                                                                                                                                                   |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 「AC 已经写得很细了，proposal 抄一遍就行」       | AC 是验收视角，proposal 是契约视角：还要补非目标、性能指标、边界、领域建模、原型契约——这些增量用户故事里没有                                           |
| 「这条 AC 太细了，合并进别的条目」               | 合并即丢失可追溯性。终审逐条核对时，合并的条目说不清哪一半没做                                                                                         |
| 「性能要求先不写，到时候再说」                   | 不写 = 默认无要求。指标必须写；验收后置测试提质 ≠ 不写                                                                                                 |
| 「边界情况实现时自然处理」                       | 边界没写进规范的特性，实现必然各处随手发挥。现在写一行，省后面一轮返工                                                                                 |
| 「交互契约实现时对着代码看就行」                 | 原型不入库，契约是唯一接口。没有可构建级契约，下游只能猜                                                                                               |
| 「文案和正则散在各条 R 里，改一处漏三处」        | E / F 表是单一事实源：文案、规则各只定义一次，其余位置引用编号                                                                                         |
| 「修订历史混在正文里，读的人分不清哪条现行有效」 | Changelog 独立成节，正文只保留当前有效状态                                                                                                             |
| 「领域模型在依赖表里一行够了，实现时自然清楚」   | 负空间与状态义务是下游最容易误加概念的地方：没有负空间表，下游会替你发明角色、验证码、找回密码；没有状态义务表，无人行动的状态会被当成待做功能排进计划 |

## 产出物

- `docs/product/AXY-<N>-<slug>/proposal.md` — 需求规范（状态：草案 → 已批准；含原型契约）
