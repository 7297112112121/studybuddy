# 架构设计（dev_architecture_design）

## 概述

开发技能组第二步：把已批准的需求规范（proposal）转化为**架构设计（design）**——数据模型、契约、UI 结构、组件划分。design 是实现计划（dev_plan_writing）的直接输入。

**页面设计统一在 design 期做**：布局与组件条目都由本技能按「先布局、后组件」两轮确认产出（proposal 契约只有文字接口，不带条目）；UI 两轮在数据模型与契约等后端大部分设计完成之后进行。

**设计原则**：易维护、可读性强。全部选型理由、风险陈述与设计判断以这两条为评审轴心。

**开始时声明**：「我正在使用 dev_architecture_design 技能为 <特性名> 做架构设计。」

## 硬门禁（HARD-GATE）

1. **design 主文件与全部拆出文件未获人工批准，不得拆分任务、不得写任何产品代码。**（这是第二道批准门；第一道在 proposal。）
2. **新增文件落点必须在代码目录清单内。** `docs/dev/代码目录.md` 的目录树与业务模块形状是 `src/` 落点的封闭清单；清单装不下的落点是设计缺陷，登记开放问题经开发者裁定，不得就近发明目录。结构性阻塞——多处落点装不下、需变更模块形状或数据流向——超出单特性可裁定范围，提示回流 architecture_evolution，不在本技能内裁决清单变更。
3. **关键决策不得由 AI 单方拍板。** 影响接口形状、状态归属、文件落点、组件划分的决策点，逐点给选型供开发者选择（纪律见流程 3）。

## 分支衔接

**流程前后继**：上游——product_proposal_writing（已批准 proposal 已合并进 `master`）；下游——dev_plan_writing（承接已批准 design）。

本技能是 feat 分支的开启点：开工前确认 proposal 已随 docs 分支合并进 master（未合并时先走 branch-wrapup 收尾 docs 分支），再从最新 `master` 新建 `feat/AXY-<N>-<slug>`。design 四件套落盘与批准、后续实现全部在该分支上进行。流程内产出的布局条目落 `studybuddyui/layouts/`、组件条目落 `studybuddyui/components/`，随 feat 分支一并 PR 合并进 `master`。

**批准门即页面设计基线**：提请 design 批准时，布局轮与组件轮产出的条目截图随 design 一并呈审；批准即锁定页面设计基线——其后的条目增删改走对应草稿技能（layout-upgrade / layout-remove / component-upgrade / component-remove），已批准 design 的引用按修订规则同步。

## 流程

### 1. 读 proposal 并盘点约束

proposal 位于 `docs/product/AXY-<N>-<slug>/proposal.md`，不必通读。**默认只读以下节**：

- 头部表、术语与路由、F 表、E 表、路由行为表、需求条目表（R）、边界与约束表、领域模型节、**原型契约节**（UI 交互与演示态的唯一来源——摘出演示态清单与各态布局块清单；proposal 不带布局条目引用，条目由本技能流程 4 布局轮产出）——摘出 Global Constraints 候选（校验规则、错误文案、守卫与跳转行为、边界约束）
- 范围与非目标节——摘出非目标清单，作为设计禁区，design 不得覆盖
- Q 表——只取指标名，在设计的「与 ADR 的关系」中注明去向（Q 条目**不进设计范围**，由测试提质阶段验收）

目标与背景等叙述节按需再读。

### 2. 盘点落点与既有资产

三项盘点全部主会话内联完成：

- **ADR 速查核对**：先读 `docs/dev/adr/index.md` 的「现行技术栈速查」节，本特性技术要点逐条对照；速查表给不出判定的条目才回读对应 ADR 全文，禁止「感觉一致」直接写表。子代理仅三种触发（触发时在批准请求里写一行理由）：① 要点用到速查表之外的依赖 / 服务 / 数据访问模式；② 拟偏离已接受 ADR 的硬约束；③ 人工主动提请新选型分析。无 ADR 覆盖或与 ADR 冲突时先走 ADR 流程再回来设计，不得在 design 里静默偏离。
- **代码目录清单对照**：读 `docs/dev/代码目录.md` 的目录树与业务模块形状图，盘点本特性涉及的既有模块与分层形状。设计的每个落点（新文件、新组件、新目录）都映射到清单内位置；清单装不下的落点登记开放问题经开发者裁定，不是就近发明目录。
- **既有资产盘点**：列出 `src/components/` 既有组件与 shadcn registry 可用组件（经 shadcn 工具查询可用组件与 API，不凭记忆写组件），形成复用清单——复用、组合、新建逐项有交代，作为流程 3 选型的原料。

### 3. 关键决策选型（开发者逐点选择）

判定关键决策点：影响**接口形状、状态归属、文件落点、组件划分**的决策。实现细节与纯机械选择不设选型。

每个关键决策点向开发者提交 2-4 个候选选型，每个选型三项齐备：

- **方案**：一句话说清结构或归属；
- **理由**：对照设计原则（易维护、可读性强）说明优势；
- **风险**：选它要承担什么。没有风险陈述的选型是推销。

无绝对优解时给出推荐与取舍说明；只有一条可行路径时说明缘由后按该路径设计，开发者可在批准门推翻。开发者逐点选定后落设计；决策点、候选与裁定记入 design「选型记录」节。

### 4. 产出设计

design 为**一主文件 + 三份拆出文件**，按 templates/ 模板写入 `docs/dev/AXY-<N>-<slug>/`（目录由本技能创建，编号与 slug 沿用 `docs/product/AXY-<N>-<slug>/proposal.md`；sidebar_position 依次 2 / 3 / 4 / 5）：

| 文件           | 内容                                                                                                                        | 模板                                             |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `design.md`    | 头部表（**唯一批准状态真源**）、架构总览、选型记录、范围与非目标对照、UI 与组件、错误与边界处理、需求承载对照、开放问题、拆出文件索引 | [templates/design.md](templates/design.md)       |
| `contracts.md` | 数据模型与契约（含路由行为落点表）                                                                                          | [templates/contracts.md](templates/contracts.md) |
| `testing.md`   | 测试接缝（TDD red 阶段直接输入）                                                                                            | [templates/testing.md](templates/testing.md)     |
| `adr.md`       | 与 ADR 的关系（一页纸）+ Q 条目去向                                                                                         | [templates/adr.md](templates/adr.md)             |

**批准状态单真源**：头部表只在 design.md；拆出文件头部只留一行指针「本文件为 design 的拆出节，批准状态以 design.md 头部表为准」，不另设状态列。**各节的合格判据已内联在模板中**（数据模型精确到可直接写 schema、契约精确到签名级且无「待定」、错误边界逐项对应 proposal、需求承载对照覆盖每条 R）——模板是该要求的单源，此处不重复。

**契约粒度**：契约只覆盖**跨模块 / 跨层接口**与**需单测的核心函数**；内部实现细节不写契约。

**落点纪律**：全部落点（组件、契约、schema、测试）映射到代码目录清单内位置；清单外落点登记开放问题，经开发者裁定后方可写入 design。

**UI 与组件 = 布局轮 → 组件轮，各一道显式确认门**：

**产出顺序约束——后端设计先行**：design 内先产出架构总览、选型记录、数据模型与契约（contracts.md 达签名级）等后端大部分设计，UI 两轮在其后进行。这不是流程形式：布局块与组件承载的数据和状态来自契约，契约先定型，筛选才有依据，也避免 UI 定型后契约返工连带布局重画。

**布局轮**（contracts 产出后启动，逐演示态执行）：

1. **筛选**：对照 proposal 原型契约的演示态与布局块清单，盘点 `studybuddyui/layouts/` 既有条目（看截图 `result.png` 与 `prompt.md`，禁止读条目代码），筛出可能适配的布局；
2. **呈报三类处置，经开发者确认**：
   - **无适配条目**：向开发者申请编写新布局——说明缺口（缺什么、为什么既有条目都不适配），经确认后在流程内调用 layout-draft（有参考截图/URL 或一句话页面用途均可）产出条目——方案选定、审阅归档等人工门由草稿技能承载，本技能不代走；
   - **有候选条目**：向开发者呈报候选（2-4 个）并逐个附选择理由与风险，开发者选定；
   - **豁免**：布局无争议的纯流程页，经开发者确认豁免条目，design 文字定义；
3. **确认门**：逐演示态的布局处置（引用 / 新建 / 豁免）全部经开发者确认后，布局轮闭合；候选与裁定记入选型记录。

**组件轮**（布局轮确认后启动，流程与布局轮相同）：

1. **筛选**：以确认后的布局为骨架，盘点三层既有资产——`src/components/` 既有组件、shadcn registry 可用组件（经 shadcn 工具查询，不凭记忆写组件）、`studybuddyui/components/` 草稿条目（看截图与 `prompt.md`，禁止读条目代码）；
2. **呈报三类处置，经开发者确认**：复用/组合既有组件可承载的注明来源与适配方式；无适配的向开发者说明缺口（缺的是什么）并申请调用 component-draft（有参考截图/URL 或一句话组件用途均可）产出新条目——人工门由草稿技能承载；有候选的呈报选项（2-4 个）附选择理由与风险；
3. **确认门**：逐组件的处置（复用 / 组合 / 新建 / 豁免）全部经开发者确认后闭合；每个新增组件登记**划分理由**——为什么既有组件与组合不够，「没有合适的」不算理由，说清缺的是什么——并做约 150 行红线预判。

**落节**：两轮闭合后写 design「UI 与组件」节——组件树逐组件标注 Server/Client、状态归属与职责三分类（状态机 / 组合 / 纯展示，判据见 `docs/dev/组件划分方法.md`「组件划分规则」节）；登记「条目名 → 主项目落点（组件名 / 文件）」映射；组件的状态清单（默认 / Hover / Active / Disabled 等）取自条目的全状态陈列，写入组件职责说明；经开发者确认的豁免在 UI 与组件节显式登记，不得静默留白。

**proposal 未决项处置**：影响设计前提的未决项，**须回流 proposal 追认，或在 design 开放问题中显式声明假设并标注**影响范围；仅影响测试归属的未决项可带入 design 开放问题并注明不阻塞设计。不得静默按某一方语义设计。

**裁决回写纪律**：

- **契约回写**：design 是批准工件，契约代码块永远展示**最终形态**——实现期发现设计需修正时，裁决一律记入实现计划的「裁决记录」节，design 至多留一行指针；禁止「错误原貌 + 勘误注记」并存（照抄代码块即中招）。
- **开放问题书写**：未决写「待定稿」；闭合后处置列写结论 + 证据指针，问题格保持短问题，不入内联结论。

### 5. 自查并提请批准

- [ ] 关键决策点全部经开发者选型；选型记录齐备，每项含候选、理由、风险与裁定
- [ ] 全部新增文件落点在代码目录清单内
- [ ] 既有资产盘点完成：复用、组合、新建逐组件有交代；每个新增组件有划分理由
- [ ] 组件树逐组件标注职责三分类，约 150 行红线预判无违约
- [ ] 需求承载对照表覆盖 proposal 全部 R 条目，每行有明确落点
- [ ] 每个契约都是签名级精确，无「待定」字样（待定项进开放问题并说明不阻塞什么）
- [ ] 技术选择与 ADR 全部一致或已走 ADR 流程
- [ ] 三份拆出文件（contracts / testing / adr）已落盘，头部指针行就位，无第二状态列
- [ ] 目录安排符合代码目录约定
- [ ] Q 条目未混入设计范围，去向已注明
- [ ] 非目标清单逐条未被本设计覆盖（无预留字段 / 接口 / 占位）
- [ ] 每条 R 有可测接缝（单测函数 / 集成断言点 / E2E 落点）
- [ ] E 表与路由行为表逐项有落点
- [ ] 数据模型与契约产出先于 UI 两轮（后端设计先行的顺序约束成立）
- [ ] 布局轮逐演示态经开发者确认：引用 / 新建 / 豁免处置有记录，候选呈报附理由与风险
- [ ] 组件轮在布局轮确认后启动，逐组件处置（复用 / 组合 / 新建 / 豁免）经开发者确认
- [ ] 布局与组件条目截图随 design 一并呈审；每个新组件有条目 → 落点映射，或豁免已显式登记

自查通过后提请人工批准，状态改为「已批准」。

## 合理化对照表

| 借口                                                | 现实                                                                                                                                                  |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「这个选型 obviously 对，ADR 以后补」               | 无 ADR 的选型 = 下次重构时没人知道为什么。先 ADR 后设计，顺序不能反                                                                                   |
| 「拿不准和 ADR 一不一致，派个 subagent 核一遍保险」 | 已接受技术栈的核对是查速查表，内联 5 分钟对完。subagent 核已接受技术 = 白付一次冷启动；只有新选型 / 拟偏离 / 人工要求才值得派                          |
| 「最优解显而易见，选型是走过场」                    | 没摆上桌的选项等于没被考虑过。开发者要的是选择权——被知会的候选才有被否决的机会；批准时才发现方向不对，是全流程最贵的返工                               |
| 「清单外先建个 utils/ 放着，目录约定以后再补」      | 代码目录清单是封闭的：清单外位置对审查者是陌生地形，对实现者是随意的开始。缺位置先裁定，落点失控一步就会演变成自创文件满天飞                           |
| 「组件先建起来，臃肿了再拆」                        | 拆一个被依赖的臃肿组件，成本远高于设计期一次划分。划分理由写不出来 = 还没想清楚它该是什么                                                             |
| 「契约写个大概，实现时再细化」                      | 契约不精确，plan 的 Interfaces 块就是空话，任务间靠猜对齐                                                                                             |
| 「组件长相实现时顺手定就行」                        | 组件效果是开发者逐个确认的条目。实现期再定 = 页面外观回到 AI 自由发挥                                                                                 |
| 「后端契约没写完，先把 UI 画出来并行赶进度」        | UI 承载的数据与状态来自契约。契约未定型就筛布局，契约一改布局重画——顺序约束省的是返工不是形式                                                          |
| 「布局 proposal 期就该顺手定掉，design 再筛是重复劳动」 | proposal 契约只有文字接口，没有视觉确认点；布局条目与数据契约对齐后筛选才筛得准。proposal 期出条目，契约一改就返工                                     |
| 「这个功能很小，架构设计可以跳过」                  | 那它就不该有自己的 proposal。凡有 proposal 必有 design，规模小就写短                                                                                  |
