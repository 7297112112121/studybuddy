# 特性推翻/取代/废弃（feature-supersede）

## 概述与定位

**横切技能**：不在 product-design → proposal-writing → architecture-design → plan-writing → spec-review 的单向流内，任意阶段可触发。触发条件：**特性已走完完整开发流程并合并主分支**，而其用户故事需要推翻重写、被新特性取代、或整个废弃。未合并的特性不适用——直接修订工件并重走批准门即可，不需要本技能。

本技能只定义「变更管理」这一层：定级、冻结、重新批准、代码处置、墓碑留痕、变更记录。四技能的既有门禁一律**引用而非复述**：故事与 proposal 的批准门见 product-design / proposal-writing，契约纪律见 architecture-design，TDD 门禁见 plan-writing，证据门禁见 spec-review——需要时指向对应技能，不复制其规则细节。

**开始时声明**：「我正在使用 feature-supersede 技能处理 <特性名> 的推翻/取代/废弃。」

## 硬门禁（HARD-GATE）

1. **未定级不得动手**：未完成 A/B/C/D 定级（见「定级表」）与下游影响评估，不得改 story、proposal 或任何产品代码。
2. **未重新批准不得改产品代码**：story 与 proposal 重新批准前，代码只允许「冻结」（停止该特性的一切新增修改）；回滚 / 删除属于变更执行，须在批准后。
3. **不得改写主分支历史**：禁止 force push、禁止 rebase 已合并提交、禁止 `reset` 已合并历史；整体回滚用 `git revert -m 1 <merge-commit>`，并打 tag 标记废弃点。
4. **旧工件不删除，只加墓碑**：旧 story / proposal / design / tasks / review 保留原文，按「墓碑动作表」更新头部状态区；旧测试不得留作假绿——失效测试删除或 skip 并注明原因与关联变更记录编号。

## 边界（与其他技能的关系）

- **引用不复述**：批准门、契约纪律、TDD 门禁、证据门禁只引用（见概述）；本技能的产出（新 story、新或修订 proposal、重走的 design / tasks / review）仍走各自所属技能与门禁。
- **A 级轻量路径**：A 级表述变化只做阶段 1、3、6 的轻量版（更新 story + proposal Changelog + 变更记录），不强制重走 design / plan / review；**但仍须重新批准**——批准覆盖文档当前内容的纪律不因轻量而豁免。
- **与 spec-review 的关系**：被推翻 / 废弃特性的旧 review 加墓碑后**不参与**新实现的终审判定，新 review 只审新实现；变更记录（`change-record.md`）是 spec-review 判断「哪些代码是活的」的依据。
- **下游特性**：本技能只负责评估与通知下游，不替下游做变更；下游各自走本技能或自己的修订流程。

## 流程（六阶段）

### 1. 定级与依赖评估

- **输入**：旧 story / proposal / design / tasks / review 全部工件、现有代码、下游特性清单（docs/product/index.md）。
- **动作**：按「定级表」定级；回答三个必答问题——①是否触及 R 条目？②是否触及数据模型或对外契约？③下游是否已依赖（账号表、会话工具函数、路由常量等逐点排查）？
- **产出**：定级结论 + 下游依赖点清单。
- **判据**：级别有判据支撑（引 R 编号 / 表名 / 负空间行）；三问逐条有答案，「下游无依赖」须写明查证方式。

### 2. 冻结与止损

- **输入**：阶段 1 的定级结论与下游清单。
- **动作**：冻结该特性开发（停止一切新增修改）；story 与 proposal 头部状态标记「需重审」；通知下游持有者与提出者。
- **产出**：冻结通知与状态变更。
- **判据**：状态标记先行于任何内容修改；通知覆盖全部下游依赖点。

### 3. story 重写并重新批准

- **输入**：旧 story + 定级结论。
- **动作**：C / D 级——旧 story 加墓碑全文保留，新版本按 product-design 流程重新澄清落盘（C 级另起新编号，编号不复用），重走 DOR 与批准门；A / B 级——story 按新语义更新并在状态行注记修订依据，重新批准。
- **产出**：新 story + 批准记录。
- **判据**：新版批准日期晚于本变更记录；C / D 级旧版正文未改写（墓碑只动头部状态区）。

### 4. proposal 处置（三选一，必须显式）

- **输入**：已批准的新 story + 旧 proposal。
- **动作**：**修订**（B 级：升版本，废止条目保留编号进 Changelog，如实写明「语义已变」或「语义未变」）/ **新建**（C 级：旧 proposal 标「已被 AXY-<M> 取代」，新编号不复用）/ **废弃**（D 级：标「已废弃」并解除下游），按 proposal-writing 流程重走批准门。
- **产出**：proposal 处置决策 + 变更后 proposal。
- **判据**：处置与定级一致；推翻 / 取代场景语义默认「已变」，写「未变」须附逐条 R 核对依据。

### 5. 代码处置（四选一，必须显式）

- **输入**：变更后 proposal 的处置结论。
- **动作**：按「代码处置表与 Git 铁律」执行，留存 Git 引用（commit / tag）。
- **产出**：代码处置决策 + Git 引用。
- **判据**：处置在重新批准之后执行（硬门禁 2）；Git 引用真实可查；旧测试按表处理，无假绿。

### 6. 墓碑留痕 + 变更记录 + 重走下游客

- **输入**：前五阶段全部产出。
- **动作**：按「墓碑动作表」逐工件加墓碑；按 [templates/change-record.md](templates/change-record.md) 写入 `docs/product/AXY-<N>-<slug>/change-record.md`；按新 proposal 重走 design → plan → review（各走自身技能）；保留部分须作为既有资产核对契约与数据模型兼容性（落新 design 的对应节）。
- **产出**：带墓碑的旧工件 + 变更记录 + 重走的新 design / tasks / review。
- **判据**：墓碑清单逐工件登记（不存在的工件注明）；变更记录八节齐全；处置完成后全量测试套件绿（证据进变更记录第 8 节）。

## 定级表

| 级别 | 判据 | 典型例子 | 操作路径 |
| - | - | - | - |
| A 表述变化 | 仅叙述 / 背景 / AC 措辞变，R、数据模型、对外契约不变 | 「学生」改「学习者」 | 更新 story + proposal 引用与 Changelog，代码不动，轻量批准 |
| B AC 变化 | 部分 R 失效 / 新增，F / E 或数据模型变，定位不变 | 手机号注册改为手机号或邮箱注册 | 修订 proposal 升版本；代码部分回滚 / 改造；重走下游客 |
| C 定位变化 | 目标用户或核心价值变，大部分 R 与数据模型作废 | 学生记账改为教师布置作业 | 旧 proposal 标「已被取代」，新建 proposal 新编号；代码整体回滚或删除；全量重走 |
| D 废弃 | 特性不做了 | 产品方向调整 | proposal 标「已废弃」；代码回滚；下游解除依赖 |

## 代码处置表与 Git 铁律

| 处置 | 适用 | 做法 | 旧测试处理 |
| ---- | ---- | ---- | ---- |
| 保留 | A 级 | 代码不动 | 保留 |
| 部分回滚改造 | B 级 | 被替换模块先 revert 对应 commit，再按新 design 实现；新增迁移不改旧迁移 | 被替换行为的测试删除；保留部分的测试继续生效 |
| 整体回滚 | C / D 级 | `git revert -m 1 <merge-commit>` 并打 tag；已应用的迁移文件不随 revert 删除，表结构清理（如需）以新增迁移承载 | 随 revert 一并移除；回滚后全量套件须绿 |
| 标记废弃暂不删 | D 级（有解除期限时） | 代码原地保留、入口断开，头部注释标废弃 + 变更记录编号；**须设删除期限与责任人** | skip 并注明原因与变更记录编号 |

**Git 铁律**：

- 禁止 force push；禁止 rebase 已合并提交；禁止 `reset` 已合并历史；
- 整体回滚一律 `git revert -m 1 <merge-commit>`；
- 处置点打 tag：`axy-<N>-superseded-YYYY-MM-DD`（C 级）/ `axy-<N>-deprecated-YYYY-MM-DD`（D 级）；
- 数据迁移新增不改旧，已应用迁移不随代码回滚删除；
- 全部 Git 引用（commit / revert commit / tag）写入变更记录第 5 节。

## 墓碑动作表

适用于被作废 / 取代 / 废弃的工件（B / C / D 级）；A 级与修订后仍有效的工件按原所属技能的修订纪律更新，不加墓碑。墓碑只动头部状态区（frontmatter status / 状态行 / 头部表），正文与契约代码块保留原貌不改写——引用即原样。

| 工件 | 状态改为 | 头部追加 | 正文处理 |
| ---- | ---- | ---- | ---- |
| story（docs/product） | 已被取代 / 已废弃 | 被哪版取代、原因、日期、变更记录链接 | 保留全文 |
| proposal（docs/product） | 已被 AXY-<M> 取代 / 已废弃（frontmatter status 同步） | 取代者编号、原因、日期 | 保留（含原型契约）；Changelog 终条登记本次处置 |
| design（docs/dev） | 已被取代 / 已废弃 | 处置结论 + 实现基线 Git 引用（revert commit / tag） | 保留全文 |
| tasks（docs/dev） | 已废弃 / 已被取代 | 实现已回滚 / 废弃的 Git 引用 | 保留；裁决记录保持历史原貌，不新增任务 |
| review（docs/dev） | 历史报告（判定结论不改） | 注明「针对的实现已废弃 / 已回滚，不得作为新 review 依据」+ Git 引用 | 保留全文 |

## 变更记录字段

变更记录（`change-record.md`）是四技能之外的**第五份工件**，落 `docs/product/AXY-<N>-<slug>/`，是未来 spec-review 判断「哪些代码是活的」的依据。必填字段：变更编号（CR-<YYYYMMDD>-<N>）与日期、定级与判据、下游影响、story 变更、proposal 处置（三选一 + 编号策略 + 语义是否变化 + 废止条目编号清单）、代码处置（四选一 + Git 引用 + 旧测试处理 + 迁移处理）、墓碑清单、重走下游客、证据。结构与各节内联合格判据的单源在 [templates/change-record.md](templates/change-record.md)，此处不重复。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「先改代码，文档后面补」 | 未重新批准不得改产品代码。代码先行 = 批准门倒置，返工的是代码不是文档 |
| 「直接改 story 内容就行」 | story 是批准工件，改内容 = 旧批准失效。重走批准门，否则门形同虚设 |
| 「回滚就 git reset」 | 已合并历史不可改写。revert + tag 留下可审计的处置点 |
| 「旧文档删了清爽」 | 墓碑保留。删了旧工件，未来的人无法理解「代码为什么长这样」 |
| 「旧测试留着还能跑」 | 假绿制造「功能还在」的假象。删或 skip 并注明原因与变更记录编号 |
| 「下游以后再说」 | 下游耦合不先评估，回滚粒度就是拍脑袋。先列依赖点再定处置 |
| 「语义没变，套旧 Changelog 惯例」 | 推翻重写大概率语义已变。如实写「已变」，写「未变」须附逐条 R 核对依据 |
| 「补丁很小，不值得走流程」 | 定级看触没触及 R / 数据模型 / 契约，不看改动行数。B 级小补丁也要重新批准 |

## 产出物

- `docs/product/AXY-<N>-<slug>/change-record.md` — 变更记录（第五份工件）
- 带墓碑的旧工件 — story / proposal / design / tasks / review 就地更新头部状态区
- 新 story / 新或修订 proposal — 按处置（A / B 级为修订，C 级为新编号）
- 代码处置的 Git 引用 — commit / revert commit / tag
- 重走下游客的新 design / tasks / review — A 级轻量路径不适用
