# 产品设计（product_design）

## 概述

产品技能组的第一技能，负责把一个模糊的想法澄清为**落盘的用户故事**。故事严格由五大组成部分构成——故事陈述、验收标准、故事点、优先级、完成定义——一页纸以内。范围界定、非目标、领域建模、原型契约等规范内容一律不进故事，由产品侧的下游需求规范（proposal，product_proposal_writing 技能产出）承载。

**开始时声明**：「我正在使用 product_design 技能将这个想法转化为用户故事。」

## 何时使用 / 不使用

**使用**：用户提出的是未经结构化的想法——一句话需求、一个痛点、一个功能愿望，尚未形成用户故事。

**不使用**：

- 用户故事已存在于 docs/product——直接进入 product_proposal_writing；
- 想法属于纯技术决策（选库、目录结构等）——走 ADR 流程；
- 对既有用户故事的修订——直接编辑对应文档，但若修订触及验收标准，须同步通知下游 proposal 持有者。

## 硬门禁（HARD-GATE）

1. **用户故事未经人工批准，不得进入开发落地。** product_proposal_writing 以「已批准的用户故事」为输入前提；未批准的故事状态标记为「草案」。
2. **spike 一次性原型一律不入库。** 澄清期的 spike 看完即弃；页面设计的入库资产由下游承载——proposal 的「原型契约」（文字接口，product_proposal_writing 维护）与 `studybuddyui/` 布局草稿条目（视觉真源，经 layout-draft 产出）。
3. **AXY 编号由项目管理平台生成。** 技能与 AI 不得自行分配、顺延或复用编号。新故事先产出名单（名称 + 一句话内容 + 依赖）向提出者申请编号；取号后的落盘动作见流程 5。
4. **单故事迭代。** 一次只澄清与落盘一个故事；发现多个独立故事时先切割、逐个处理，禁止批量产出。

## 分支衔接

**流程前后继**：上游——无（流程起点，输入模糊想法）；下游——product_proposal_writing（承接已批准用户故事）。

本技能是 docs 分支的开启点：创建用户故事时，若当前不在对应分支，从最新 `master` 新建 `docs/<slug>`（slug 与特性对应；取号在分支上进行，编号下发后不重命名分支）。侦察、澄清、落盘、批准全部在该分支上进行。

## 流程

### 1. 侦察

读 docs/product/index.md 用户故事总览、相邻故事与 docs/intro.md，盘点既有领域实现。**不问项目与文档已回答的问题，不重开已决定的事项。** 证据收集可派子代理并行（prompt 必须自包含：写明查什么、返回什么格式），环境不支持时内联执行并明说；向提出者的提问与最终裁决永远由主会话完成，不委派。

### 2. 澄清对话

按 [references/questioning.md](references/questioning.md) 的协议进行：先开放题探 why，后选项式收敛；一次一问；每问必须改变产物；分段回放；归属标注。方向错误的成本远大于提问的成本。

对话只收敛两样东西：**故事陈述**（角色处境 / 动作 / 价值，三段齐全、一句话）与**验收标准**（含空态 / 异常 / 并发等边界）。范围与非目标不是本阶段的产物——留给 proposal。

### 3. 切割判定与循环拆解

判据：一故事一目标，故事陈述超过一句话即两个用户目标，必须拆分；验收标准 ≤ 6 条，6–8 条须在故事文档登记豁免理由，> 8 条必拆。

**拆解是循环，不是一次性判断**。体量过大的需求（如「统计中心含日统计、打卡、周报、排行榜、导出」一口气说五件事）往往切一刀还切不开：

1. 用上面的判据检查当前需求；
2. 不过 → 按用户目标切出子故事名单——名称 + 一句话内容 + **依赖**（写明本故事要读取哪个兄弟故事的产出才能成立）——向提出者申请新编号（见硬门禁 3）；
3. **逐一回到第 1 步检查每个子故事**：仍超限就继续切，循环到名单里每个故事都通过判据为止。循环结束时不存在「以后再拆」的悬置故事。

**依赖关系决定先后**。全部子故事达标后，把依赖关系摆成一张先后图，据此指出**第一个进入 proposal 的故事**——自身无依赖或依赖最少、且被别人依赖的最上游故事（下游都压在它上面，它不动后面全堵）。拆分结论与先后顺序一并提请提出者确认，确认后登记进 `docs/product/index.md` 与各故事「依赖」字段。

循环只产出名单与顺序，**澄清与落盘仍一次只做一个故事**（硬门禁 4）：先做排头故事，走完整个流程再轮到下一个。

### 3.5 语言纪律：故事只用用户的语言

故事陈述与验收标准的读者是使用产品的人，其中**禁止出现实现层的技术词汇**——路由、页面路径、API、接口、数据库、缓存、token、组件、前端/后端、状态管理等。这条纪律存在的原因：用技术词写的故事会把实现方式偷偷焊死进需求，验收时无法用界面观察来判定。

提出者用技术词描述想法时（如「在 / 路由加个入口」「数据存到数据库」），先翻译成用户能看到、能做到的事再写进故事：

- 「在 / 路由看到打卡入口」→「打开首页看到打卡入口」；
- 「存进数据库」→ 关心其用户可感知的结果，如「换个设备登录后还能看到」。

自检方法：把故事念给目标用户听，出现他不懂的词就是犯规，改写后重念。用户自己可感知的产品概念（账号、扫码、通知）不算技术术语。DoD 的「工作项」是写给开发团队的验证条目，不受本条约束。

### 4. （可选）spike 一次性原型

争议交互或说不清的体验，可做一次性原型给提出者看。规范：

| 规则     | 内容                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 形态     | 单文件 HTML，双击即开，无构建、无本地依赖（可用 CDN）；原生或 React(babel-standalone) 皆可 |
| 必含     | 至少一个非 happy-path 态（空态 / 失败态）——只有顺利路径的原型是在为缺失的状态背书          |
| 位置     | 本地临时目录（如系统临时目录），**不提交、不入库**                                         |
| 生命周期 | 看完即弃；有价值的结论回灌对话与故事；**产物转正 = 新请求，重新过批准门**——提出者认可的 spike 可另走 layout-draft 转正为布局草稿条目，入库与批准由 proposal 流程承载 |
| 时机     | just-in-time：只在提出者需要看、或交互争议无法用文字收敛时做；不预先生成；被拒后不再提     |
| 自查     | 交付给提出者看之前自查明暗两色、窄屏可用；低保真即可，重点是状态与交互可操作               |

### 5. 落盘故事

落盘两段式：

- **编号未下发**：按 [templates/user-story.md](templates/user-story.md) 以「待编号」平铺写入 `docs/product/<feature>.md`。
- **取号后同一动作**：创建 `docs/product/AXY-<N>-<slug>/` 目录（目录由本技能创建），迁入 `story.md`，回填编号，并在 `docs/product/index.md` 总览表登记一行。

DoD 不复制样板：唯一真源是本技能 [references/dod.md](references/dod.md)，故事只登记「工作项（本故事特有）」。

### 6. DOR 自检与提请批准

逐项核对 DOR：故事陈述一句话且三段齐全、验收标准可测试、粒度单 Sprint 可完成、依赖已识别、**故事陈述与验收标准无技术术语**（见 3.5）。**DOR 是流程动作，不落盘成表**：自检结论记入文档头部状态行。缺口未闭合不得提请批准——用户故事不设「开放问题」节，收敛不完就继续对话或拆分。全部通过后向提出者请求批准；批准后状态行改为「已批准」并附日期。**批准覆盖文档当前内容：其后再改须重新确认。**

## 反模式对照表

| 借口                                     | 现实                                                                                          |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| 「先甩一版选项菜单让用户挑」             | 选项会锁死想象。why 未明只用开放题，让提出者自己描述                                          |
| 「我先填个合理默认值」                   | 默认值必须说出口。没听过的默认无法被否决                                                      |
| 「想法够清楚了，直接写故事」             | 你觉得清楚 ≠ 提出者觉得清楚。未提问产出的故事，AC 是猜的                                      |
| 「范围 / 非目标 / 交互细节顺手写进故事」 | 故事只装五大组成部分。规范内容是 proposal 的职责，提前写 = 过度设计，还会与 proposal 重复打架 |
| 「边界后面再定」                         | 没有边界 AC 的故事，验收时必然扯皮。边界情形写进 AC；范围层面的取舍留给 proposal              |
| 「故事没批准，先做个原型看看」           | 批准门前只允许 spike 且不入库；故事没批准就做原型 = 过度提早设计                              |
| 「spike 能跑，直接在它上面继续做」       | spike 转正是新请求，回批准门重来                                                              |
| 「这几个故事类似，一批写完快」           | 批量产出 = 一次写一整页再切 AC 的老路。一次一个故事                                           |
| 「DOR 差一项也先开工」                   | 差一项就不是就绪。继续对话收敛，或拆分，没有第三条路                                          |
| 「提出者说『/ 路由』『存数据库』，照抄进故事」 | 故事是写给用户的。技术词先翻译成用户可感知的界面结果再落笔（见 3.5），否则实现被焊死进需求 |
| 「切了一刀够小了，不用再回头看」         | 子故事同样超限时必须继续切。循环到每个故事都过判据才收口，并依依赖定出第一个进 proposal 的故事 |

## 产出物

- `docs/product/AXY-<N>-<slug>/story.md` — 用户故事（目录由本技能创建；编号未下发时先按流程 5 平铺暂存于 `docs/product/<feature>.md`，取号后同一动作迁入）
- `docs/product/index.md` — 用户故事总览表新增一行（编号来自项目管理平台）
- （临时）spike 一次性 HTML — 不入库，看完即弃
