# 实现计划编写（plan-writing）

## 概述

开发技能组第三步：把已批准的架构设计拆解为**微任务实现计划**。计划写给一个没见过这段对话、但会写地道代码的实现者——他们能做对一切计划留白处的合理选择，做不对的是你已决定的事：哪些文件、哪些名字与签名、需求里的哪些值、哪些测试证明哪个任务。把这些写下来。

**开始时声明**：「我正在使用 plan-writing 技能为 <特性名> 编写实现计划。」

## 硬门禁（HARD-GATE，对一切产品代码生效）

**无先失败的测试，即无产品代码。** 单元、集成、E2E 测试一律先红后绿——包括集成与 E2E：它们是任务拆分中的**显式任务**，不是实现完成后的收尾补写；先写实现再补测试 = 按实现写测试，测试永远通过但不测边界。

## 保存位置

`docs/dev/AXY-<N>-<slug>/tasks.md`（与 design 同目录；proposal 位于 `docs/product/AXY-<N>-<slug>/`，目录名沿用其编号与 slug，计划自身的日期写进头部 Date 行）

## 第 1 步：读 design 并盘点

计划的第一动作是通读**已批准的 design**（`docs/dev/AXY-<N>-<slug>/design.md`），把其结构逐节盘点为任务原料，而不是直接按 proposal 的 R 表拆任务。各节 → 任务的派生规则：

- **契约表**：每个契约（签名 + 调用方/被调方 + 错误情形）至少一个任务；标有错误情形的契约，该情形至少一条失败测试（错误情形随签名抄入任务卡 Interfaces 行）；
- **数据模型与状态转换表**：迁移 / schema 任务；每个状态转换至少一个测试任务；
- **UI 与组件**：组件任务；演示态 ↔ AC 映射 → 每个演示态至少一个 E2E 任务，跨 R 的演示态在此对齐（任务卡 AC / 演示态 行必填）；
- **错误与边界处理（边界表 + E 表映射）**：逐条对应失败测试，呈现位置（字段下/表单提示区/勾选框旁）写进断言；
- **需求承载对照（含可测接缝列）与测试接缝节**：每个可测接缝至少一个任务，任务卡「失败测试」行直接取自接缝；
- **范围与非目标对照**：逐条摘出「不安排任务」清单写入计划（模板有对应节），执行期不得为其临时加任务；
- **开放问题**：假设声明进 Global Constraints 或 Review Focus——实现者必须知道自己在哪个假设下写代码；
- **与 ADR 的关系**：强约束（版本锁定、端点禁用等）进 Global Constraints。

proposal 在盘点中的角色是对照源：R 表（含测试层列与状态列，状态「废止」的条目不安排任务）、E 表、路由行为表、边界表、演示态清单，用于核对 design 落点无遗漏。**不得只按 proposal R 表拆任务**：design 的每条契约、数据模型与状态转换、错误边界、演示态、可测接缝，都必须有承载任务，或明确说明由哪个任务的哪个测试覆盖。

## 计划结构

按 [templates/tasks.md](templates/tasks.md) 的骨架写入，各行的合格判据见模板内联说明：

- **计划头部**：Goal / Date / Spec / Design 路径 + **Global Constraints**（proposal/design 全局要求逐行照抄，值不转述，判据见模板）+ **不安排任务**（design 非目标对照逐条落名，防执行期临时加任务）+ **Review Focus**（spec 与 design 隐含但无任务测试覆盖、最可能咬到真实使用者的失效模式，按风险排序不设硬上限，每行必须有测试固定在对应任务）；
- **执行纪律**：模板已在全局声明一次 TDD 六步（写失败测试 → 确认失败 → 实现 → 确认通过 → 全量套件 → 提交），任务卡只写差异——文件、签名、失败测试、预期失败、提交信息，不逐任务重复六步；
- **裁决记录节**：预留在计划尾部，承接执行期的偏离入档（见「执行交接」）。

## 粒度规则

- **任务**：最小可独立携带一个测试循环、值得一次独立审查的单元。脚手架、配置、文档类步骤折叠进需要它的任务；只有当审查者可能通过一个任务而否决其邻任务时才拆开。
- **步骤**：执行以模板「执行纪律」声明的 TDD 六步为准，每步一个动作 + 一个可检查结果；任务卡不为六步留重复位置，只写差异。
- **比例**：计划比它描述的代码还长，就说明它写成了代码的转写。签名与测试名能决定的，不抄函数体。

## 集成与 E2E 任务

在单元任务之后安排独立的集成/E2E 任务，同样先红后绿：先写失败的集成/E2E 用例（对应 proposal 验证方式标「集成测试 / E2E 测试」的需求条目），确认失败，再补齐让它通过的胶水。禁止「先实现等集成时再补测试」。

## 迁移与 schema 任务

迁移 / schema 同样先红后绿：先写「查库断言列 / 索引不存在」的失败测试并跑红，再写迁移，再跑绿；唯一索引与并发约束用集成测试先红后绿（如并发提交同一手机号注册仅一次成功）。禁止「先写迁移再补查库断言」的倒序——迁移先行则断言永不红，约束等于没测过。

## 自查（写完后以新鲜眼光对照 spec 与 design 过一遍）

1. **需求覆盖**：proposal 每条 R（状态「废止」的除外）都能指出承载它的任务；查出的缺口补任务；
2. **步骤扫描**：每步让实现者只能写出一个合理的东西；决定不了任何事的行（「处理边界情况」「加适当校验」）是缺口，函数体已由签名与测试决定的抄写是转写，两者都改；
3. **类型一致性**：后面任务用到的名字/类型与前面任务 Produces 的完全一致。Task 3 叫 `clearLayers()` 而 Task 7 调 `clearFullLayers()` 是 bug；
4. **Review Focus**：每行都有测试固定在对应任务里；
5. **Q 条目核对**：性能与质量要求（Q 条目）一律不安排验证任务（测试提质阶段验收）；R 条目一条不漏；
6. **design 覆盖**：design 的每个契约（含错误情形）、数据模型与状态转换、E 表映射、演示态、可测接缝均有承载任务；
7. **失败测试与接缝**：每个契约的错误情形至少一条失败测试；每条可测接缝至少一个任务；
8. **非目标一致**：「不安排任务」清单与 design 非目标对照逐条一致，无预留任务。

## 执行交接

计划保存并自查后，交人工审阅，等待确认后再开始执行。执行方式（逐任务派子代理、或本会话内联执行）由人选择；逐任务派子代理时，**子代理 prompt 必须自包含**（该任务卡全文 + Global Constraints + 其 Consumes 的 Interfaces 契约），不得依赖本会话上下文——任务卡就是为此设计的最小交接单元；环境不支持子代理时内联执行并明说，不得假装已委派。执行中发现的计划缺陷记入计划的「裁决记录」节：`裁决: <决定了什么> — <为什么> — <错了的代价>`，不停摆等人。裁决只进裁决记录节，不改写 design 的契约代码块（design 侧留痕至多一行指针，见 architecture-design 技能的裁决回写纪律）。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「计划这么细了，写代码是抄」 | 那是计划写过了头。签名 + 测试名 + 断言足够，删函数体 |
| 「集成测试等写完一起补」 | 补的测试没红过 = 没测过。集成/E2E 是显式任务，先红后绿 |
| 「这步太简单，合并描述就行」 | 合并后「可检查的结果」就没了。简单就写短，不写含糊 |
| 「执行时遇到再改计划就行」 | 没记录的偏离 = 计划与实现各说各话，终审对不上。裁决入档 |
