# 实现计划编写（plan-writing）

## 概述

开发技能组第三步：把已批准的架构设计拆解为**微任务实现计划**。计划写给一个没见过这段对话、但会写地道代码的实现者——他们能做对一切计划留白处的合理选择，做不对的是你已决定的事：哪些文件、哪些名字与签名、需求里的哪些值、哪些测试证明哪个任务。把这些写下来。

**开始时声明**：「我正在使用 plan-writing 技能为 <特性名> 编写实现计划。」

## TDD 铁律（对一切产品代码生效）

```
无先失败的测试,即无产品代码
```

- 单元、集成、E2E 测试一律先红后绿——包括集成与 E2E：它们是任务拆分中的**显式任务**，不是实现完成后的收尾补写；
- 先写实现再补测试 = 按实现写测试，测试永远通过但不测边界。「未看着测试失败，即未测过。」

## 保存位置

`docs/dev/AXY-<N>-<slug>/tasks.md`（与 proposal、design 同目录；目录名沿用 proposal 的编号与 slug，计划自身的日期写进头部 Date 行）

## 计划头部（每个计划必须以此开头）

```markdown
# <特性名> 实现计划

**Goal:** <一句话:构建什么>

**Date:** <YYYY-MM-DD>

**Spec:** docs/dev/AXY-<N>-<slug>/proposal.mdx（需求规范,权威）
**Design:** docs/dev/AXY-<N>-<slug>/design.mdx（架构设计,契约来源）

## Global Constraints

<proposal/design 的全局要求,逐行一条,值原样照抄:版本下限、命名与文案规则、
性能指标(含已豁免项的注明方式)。每个任务的要求都隐含本节。>

## Review Focus

<spec 隐含但没有任何任务的测试覆盖、且最可能咬到真实使用者的五类输入或
失效模式——每行一条,写明输入/条件与合理预期,最可能者在前。
对每行,在拥有对应代码的任务里补一个固定它的测试步骤。
空节表示"查过且没有",不是"没查"。>
```

## 任务结构

```markdown
### Task N: <组件名>

**Files:**
- Create: `精确/路径/文件.ts`
- Modify: `精确/路径/既有.ts:<行号范围>`
- Test: `测试/路径/文件.test.ts`

**Interfaces:**
- Consumes: <使用前面任务的哪些产物——精确签名,抄自 design 契约表>
- Produces: <后面任务依赖什么——函数名、参数与返回类型。
  实现者只看得到自己的任务,这个块是他们得知相邻任务所用名字与类型的唯一途径。>

- [ ] **Step 1: 写失败测试**

<测试代码:名称与断言,spec 的精确值写在里面>

- [ ] **Step 2: 运行测试,确认以预期方式失败**

Run: `<测试命令>`
Expected: FAIL,<预期的失败原因>

- [ ] **Step 3: 在 `精确路径` 实现 `<签名>`**

<签名已定时不再写函数体;仅当签名与测试都无法决定算法时给一个代码块>

- [ ] **Step 4: 运行测试,确认通过**
- [ ] **Step 5: 运行全量测试套件,确认全绿**
- [ ] **Step 6: 提交**
```

## 粒度规则

- **任务**：最小可独立携带一个测试循环、值得一次独立审查的单元。脚手架、配置、文档类步骤折叠进需要它的任务；只有当审查者可能通过一个任务而否决其邻任务时才拆开。
- **步骤**：一个动作 + 一个可检查结果。「写失败测试」「跑它确认失败」「最小实现让它通过」「跑它确认通过」「提交」各是一步。
- **比例**：计划比它描述的代码还长，就说明它写成了代码的转写。签名与测试名能决定的，不抄函数体。

## 集成与 E2E 任务

在单元任务之后安排独立的集成/E2E 任务，同样先红后绿：先写失败的集成/E2E 用例（对应 proposal 验证方式标「集成测试 / E2E 测试」的需求条目），确认失败，再补齐让它通过的胶水。禁止「先实现等集成时再补测试」。

## 自查（写完后以新鲜眼光对照 spec 过一遍）

1. **需求覆盖**：proposal 每条 R/Q（清单内的）都能指出承载它的任务；查出的缺口补任务；
2. **步骤扫描**：每步让实现者只能写出一个合理的东西；决定不了任何事的行（「处理边界情况」「加适当校验」）是缺口，函数体已由签名与测试决定的抄写是转写，两者都改；
3. **类型一致性**：后面任务用到的名字/类型与前面任务 Produces 的完全一致。Task 3 叫 `clearLayers()` 而 Task 7 调 `clearFullLayers()` 是 bug；
4. **Review Focus**：每行都有测试固定在对应任务里；
5. **豁免核对**：豁免清单内的 Q 不安排验证任务，豁免清单外的一条不漏。

## 执行交接

计划保存并自查后，交人工审阅，等待确认后再开始执行。执行方式（逐任务派子代理、或本会话内联执行）由人选择；执行中发现的计划缺陷记入计划的「裁决记录」节：`裁决: <决定了什么> — <为什么> — <错了的代价>`，不停摆等人。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「计划这么细了，写代码是抄」 | 那是计划写过了头。签名 + 测试名 + 断言足够，删函数体 |
| 「集成测试等写完一起补」 | 补的测试没红过 = 没测过。集成/E2E 是显式任务，先红后绿 |
| 「这步太简单，合并描述就行」 | 合并后「可检查的结果」就没了。简单就写短，不写含糊 |
| 「执行时遇到再改计划就行」 | 没记录的偏离 = 计划与实现各说各话，终审对不上。裁决入档 |

## 产出物

- `docs/dev/AXY-<N>-<slug>/tasks.md` — 实现计划（含 Global Constraints、Review Focus、任务与 Interfaces 块、裁决记录节）
