# 需求规范编写（proposal-writing）

## 概述

开发技能组的入口，负责研发流程第二部分「开发落地」的第一步：把已批准的用户故事转写为一份**需求规范（proposal）**——回答做什么、不做什么、做到什么程度、边界在哪。后续的架构设计（architecture-design）与实现计划（plan-writing）都以 proposal 为准绳；终审（spec-review）逐条核对的对象也是它。

**迭代粒度：一份 proposal 对应一个特性。** 多个特性混入一份 proposal 会让规范变成大杂烩，禁止。

**开始时声明**：「我正在使用 proposal-writing 技能为 <特性名> 编写需求规范。」

## 硬门禁（HARD-GATE）

**proposal 未获人工批准，不得开始架构设计、任务拆分，不得写任何产品代码。**

## 流程

### 1. 读取用户故事（含全部引用物）

打开用户故事文档，并**沿「依赖与引用」栏回溯**：读它引用的线框图组件、依赖故事的验收标准、领域模型条目。proposal 的需求条目必须能追溯到用户故事的 AC 或开放问题的决议，不得凭空新增需求，也不得静默丢弃任何一条 AC。

### 2. 转写为需求规范

按 [templates/proposal.md](templates/proposal.md) 写入 `docs/dev/AXY-<N>-<slug>/proposal.mdx`——目录按 proposal 划分，本文件是该特性开发落地阶段的**第一手工件**，目录由此创建，后续的 design、tasks、review 都落在同一目录。核心动作：

- **做什么**：把每条 AC 转化为编号的需求条目（R1、R2…），表述可测试——终审时每条要么有对应实现与测试证据，要么在豁免清单里；
- **不做什么**：显式写出非目标。用户故事没说不做的，由本技能向提出者确认后落进「非目标」，不得留白；
- **性能与质量要求**：逐条列出可度量的指标。**可豁免但必须显式标记**（见下节）；
- **边界与约束**：输入的合法范围、异常情形、与既有特性的交互。

### 3. 豁免机制

性能（及其他质量属性）要求可豁免、移交「测试提质」阶段处理，但豁免不是消失：

- 豁免必须逐条记入 proposal 的「豁免项」表：要求原文、豁免理由、去向（测试提质）、标记日期；
- spec-review 以豁免清单为准——清单外的需求条目缺证据即判不通过；清单内的不判失败，但会在审查报告中列出供测试提质阶段反查；
- 没有豁免机制的性能要求就是纸上承诺：没人验证，审查还会卡死。

### 4. 自查并提请批准

自查清单：

- [ ] 用户故事的每条 AC 都有对应需求条目（或已列入开放问题）
- [ ] 每条需求条目可测试、无歧义表述（「适当」「合理」之类的词已消灭）
- [ ] 非目标已确认，不含糊
- [ ] 豁免项全部显式登记
- [ ] 开放问题已列出且不阻塞核心路径

自查通过后提请人工批准。批准前状态为「草案」，批准后改为「已批准」并附批准日期。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「AC 已经写得很细了，proposal 抄一遍就行」 | AC 是验收视角，proposal 是契约视角：还要补非目标、性能指标、边界——这些用户故事里没有 |
| 「这条 AC 太细了，合并进别的条目」 | 合并即丢失可追溯性。终审逐条核对时，合并的条目说不清哪一半没做 |
| 「性能要求先不写，到时候再说」 | 不写 = 默认无要求。要么写指标，要么显式豁免登记，二选一 |
| 「边界情况实现时自然处理」 | 边界没写进规范的特性，实现必然各处随手发挥。现在写一行，省后面一轮返工 |

## 产出物

- `docs/dev/AXY-<N>-<slug>/proposal.mdx` — 需求规范（状态：草案 → 已批准；同目录后续汇集 design / tasks / review）
