# 架构设计（architecture-design）

## 概述

开发技能组第二步：把已批准的需求规范（proposal）转化为**架构设计（design）**——数据模型、契约、UI 结构、组件划分。design 是实现计划（plan-writing）的直接输入。

**开始时声明**：「我正在使用 architecture-design 技能为 <特性名> 做架构设计。」

## 硬门禁（HARD-GATE）

**design 未获人工批准，不得拆分任务、不得写任何产品代码。**（这是第二道批准门；第一道在 proposal。）

## 流程

### 1. 读 proposal 并盘点约束

proposal 不必通读：**默认读头部表、需求条目表、边界与约束表、性能与质量要求表、豁免项表**，摘出 Global Constraints 候选（性能指标、边界约束、豁免清单——豁免项**不进设计范围**，但要在设计的「与 ADR 的关系」中注明去向）；目标与背景等叙述节按需再读。

### 2. 与既有 ADR、代码目录约定核对

ADR 核对**索引先行**：先读 `docs/dev/adr/index.mdx`，按本特性的技术要点只核对相关 ADR，不通读全部 ADR。核对判据：

- 有对应 ADR 且一致——照做；
- 与 ADR 冲突或无 ADR 覆盖的新选型——**先走 ADR 流程，再回来做设计**，不得在 design 里静默偏离；
- 目录与分层安排遵循代码目录文档（docs/dev/代码目录）的约定，不得另起炉灶。

ADR 核对与代码目录约定核对相互独立，可各派一个子代理并行进行——prompt 必须自包含（附设计要点清单与要读的文件），返回冲突清单与理由；环境不支持子代理时内联执行并明说。是否偏离、是否走 ADR 流程的裁决由主会话做出。

### 3. 产出设计

按 [templates/design.md](templates/design.md) 写入 `docs/dev/AXY-<N>-<slug>/design.mdx`（与 proposal 同目录，目录已由 proposal-writing 创建）。**各节的合格判据已内联在模板中**（数据模型精确到可直接写 schema、契约精确到签名级且无「待定」、错误边界逐项对应 proposal、需求承载对照覆盖每条 R）——模板是该要求的单源，此处不重复。

**裁决回写纪律**：design 是批准工件，契约代码块永远展示**最终形态**——实现期发现设计需修正时，裁决一律记入实现计划的「裁决记录」节，design 至多留一行指针；禁止「错误原貌 + 勘误注记」并存（照抄代码块即中招）。开放问题未决写「待定稿」；闭合后处置列写结论 + 证据指针，问题格保持短问题，不入内联结论。

### 4. 自查并提请批准

- [ ] 需求承载对照表覆盖 proposal 全部 R 条目，每行有明确落点
- [ ] 每个契约都是签名级精确，无「待定」字样（待定项进开放问题并说明不阻塞什么）
- [ ] 技术选择与 ADR 全部一致或已走 ADR 流程
- [ ] 目录安排符合代码目录约定
- [ ] 豁免项未混入设计范围，去向已注明

自查通过后提请人工批准，状态改为「已批准」。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「这个选型 obviously 对，ADR 以后补」 | 无 ADR 的选型 = 下次重构时没人知道为什么。先 ADR 后设计，顺序不能反 |
| 「契约写个大概，实现时再细化」 | 契约不精确，plan 的 Interfaces 块就是空话，任务间靠猜对齐 |
| 「这个功能很小，架构设计可以跳过」 | 那它就不该有自己的 proposal。凡有 proposal 必有 design，规模小就写短 |
