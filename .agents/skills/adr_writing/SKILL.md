# ADR 编写与技术选型（adr_writing）

## 概述

把选型诉求走完「澄清 → 联网查证 → 候选方案 → 落盘 ADR」全流程。一个需求常常需要**多个技术选型支撑**——如「给应用加 agent 能力」背后是智能体框架、工具权限方案、模型接入方式等多个选型职位。本技能以**职位清单 + 逐职位循环**承载这类需求：先识别需求牵涉的全部选型职位，再对每个职位完整走一遍选型流程，全部闭环后收尾汇总。

**开始时声明**：「我正在使用 adr_writing 技能为 <需求> 做技术选型。」

## 何时使用 / 不使用

**使用**：为某个职位选库/框架/服务/工具/平台的诉求——无论一句话还是一整组；`docs/dev/adr/` 正式 ADR 的新写、取代与条款级修订；`index.md` 决策日志与速查表维护。

**不使用**：

- **架构内部的决策**——数据流向、依赖方向、状态归属、模块边界、组件划分：这些是设计判断，没有候选技术可比，由 dev_architecture_design 在 design 正文与选型记录里承载，不落 ADR。
- design 的 `adr.md` 拆出文件（「与 ADR 的关系」一页纸）归 dev_architecture_design；那是 design 对既有 ADR 的对照结论，不是正式 ADR。设计中发现需要**新** ADR 时，转引本技能落 `docs/dev/adr/`。
- md/MDX 行文纪律归 doc_writing，先读它；本技能只补 ADR 特有规则。
- 未达成一致的讨论、备选分析过程：留在 design 选型记录或评审中，不落 ADR。

## 流程

### 一、识别选型职位，规划循环

从需求中提炼「为哪个职位选什么技术」的**完整职位清单**（职位 = 待选技术坐在的位置，如「智能体框架」「工具权限方案」），每个职位一句话说明它要支撑什么。表述含混的职位逐条澄清，不猜测。

清单与处理顺序同开发者确认后逐个推进。单职位需求清单只有一项，流程不变，直接进二。循环中（通常在查证阶段）发现新的依赖选型——选了 A 才暴露出 B 也需要选——追加进清单继续循环，不让它溜出清单。

### 二、澄清该职位的真实需求

与开发者确认该职位的约束：规模与性能要求、团队既有心智、与现行技术栈的兼容（读 `docs/dev/adr/index.md` 的现行技术栈速查）、许可与成本边界。需求未澄清不进入查证。

### 三、联网查证现状

盘点当前环境自己可用的联网检索手段，用它们查证每个候选技术的当前版本、维护活跃度、许可证、竞争格局等选型事实。**禁止只依靠训练集**——版本号、维护状态、生态格局持续变动，训练截止日之后的发布一律不可见，凭记忆定案等于闭眼选型。当前环境没有任何可用联网工具时，向开发者说明并请求配备；配齐之前不得落任何选型结论。查证结果注明日期与来源，直接构成 ADR 背景的选型事实。

### 四、产出 3-5 个候选方案

每个方案三项齐备：**方案**（一句话说清它是什么、放哪个位置）、**理由**（对照澄清出的需求说明优势）、**风险**（选它要承担什么；没有风险陈述的选型是推销）。给出推荐与取舍说明，交开发者选择。只有一条可行路径时说明缘由，仍须完成联网查证再按该路径推进，开发者可推翻。

### 五、落盘 ADR，推进循环

开发者选定后按 [templates/adr.md](templates/adr.md) 骨架落 ADR，写作细则（判定写还是跳过、四问与篇幅、各节合格判据、正文零引用）见 [references/adr-composition.md](references/adr-composition.md)，编号与 index 更新按 [references/lifecycle.md](references/lifecycle.md)「新写」。未选定不落盘，向开发者记录缘由后同样推进——跳过也是循环的一个合法出口。

本职位闭环（落盘或明确跳过）后，回到「一」的职位清单取下一职位，重复二至五。清单清空后收尾：核对 `index.md` 决策日志与速查表和本次落盘一致，向开发者汇总全部职位的选型结论与跳过缘由。

## 取代与条款级修订

不走选型循环的入口：开发者要求取代、推翻或条款级修订既有 ADR 时，直接按 [references/lifecycle.md](references/lifecycle.md) 对应节执行，完成后更新 `index.md`。

## 产出物

- `docs/dev/adr/NNNN-slug.md` — 每个选定职位一篇 ADR（骨架见 [templates/adr.md](templates/adr.md)）
- `docs/dev/adr/index.md` — 决策日志每篇加一行；技术栈级、带硬约束的决策同时在速查表加行
- 多职位需求另附循环收尾汇总（会话内交付，不落盘）

## 自查表

- [ ] 多职位需求已列全职位清单并逐个闭环，无遗漏、无擅自缩减；中途新增的依赖选型已进清单
- [ ] 每个职位的选型需求经澄清，约束（规模/心智/兼容/成本）齐备
- [ ] 选型事实经联网查证并注明日期与来源，非仅凭训练记忆；无联网工具时已请求开发者配备而非凭记忆定案
- [ ] 候选 3-5 个（或单一可行路径已说明缘由），每项含方案、理由、风险
- [ ] 决策是技术选型（有候选可比），非数据流向/依赖方向等架构内部设计判断
- [ ] 一 ADR 一决策；超页的内容已拆分或移往 design/plan
- [ ] 背景：数字、约束、查证过的选型事实、闭合的挂账（如有）齐备
- [ ] 决策句主动语态写死；边界逐条为可直接遵守的完整陈述
- [ ] 每个备选三项齐备，否决原因对着本产品上下文
- [ ] 后果三段齐备，负面不藏
- [ ] 正文（含状态行）零出现其他 ADR 的编号、路径或链接
- [ ] 受牵连 ADR 正文已同步，双方互不提及
- [ ] 取代时旧 ADR 仅改状态行、文件未删除；新 ADR 已把仍有效边界自足重写
- [ ] 编号 = index 最大编号 +1
- [ ] index.md 决策日志与速查表（如适用）已更新，与本次落盘一致
- [ ] doc_writing 自查表已过

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「训练数据够新，不用查了」 | 版本、维护状态、许可证、竞争格局都在变，训练截止日之后的发布一律不可见；联网查证只花几分钟，失真的选型坑一整个项目 |
| 「候选摆太多选择疲劳」 | 没摆上桌的选项等于没被考虑过；开发者要的是选择权，被知会的候选才有被否决的机会 |
| 「最优解显而易见，备选方案意思一下就行」 | 没认真写否决原因的备选，半年后会被原样重提一遍，重辩一次全价 |
| 「负面后果写了显得决策不果断」 | 后果节是诚实账不是推销稿；藏起来的代价会在实现期自己冒出来，那时更贵 |
| 「旧 ADR 被取代了，文件删掉索引干净」 | 决策记录是演化史不是现行状态页；删掉的 ADR 会让「当时为什么那么选」永远失焦 |
| 「这次修订很小，直接改旧 ADR 不另开一篇」 | 修订改的是约束条款，改错了影响面与新决策同量级；修订也要能被追溯 |
| 「背景写个大概，结论对就行」 | 前提变化时读者靠背景判断决策是否仍然成立；没有背景的结论无法被证伪，只能被盲从或盲弃 |
| 「实现细节顺手写进决策里更完整」 | 决策记录答「为什么」，实现细节答「怎么做」；混写的 ADR 在实现演进后整篇作废 |
| 「数据流向/依赖方向这么关键，也该立篇 ADR」 | 关键不等于选型：没有候选可比的设计判断写进 ADR，决策记录就成了第二份设计文档；它的家在 design 正文与选型记录 |
| 「放个链接跳过去多方便，删了可惜」 | 正文里的路径把两篇决策焊死在对方的文件位置上，改名、移动、被取代都会失链；跳转找 index.md，正文只管把自己的决策讲完 |
| 「承 ADR-XXXX 第 N 项比重写一遍省事」 | 引用把「现在有效的到底是什么」外包给另一篇文件，读者必须两头对照才能拼出现状；重写一遍，单篇即可读懂 |
| 「需求一句话，选完第一个顺手把剩下的也定了」 | 第一个职位的结论不替其他职位做决定；每个职位各有约束与候选，跳过澄清与查证的选型是拿本职位的风险垫别的职位 |
