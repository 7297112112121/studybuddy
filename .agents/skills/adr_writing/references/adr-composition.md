# ADR 写作细则（adr_writing）

落盘 ADR 前读本文件：判定写还是跳过、四问与篇幅、各节合格判据、正文零引用。骨架按 [templates/adr.md](../templates/adr.md)。

## 判定：写还是跳过

ADR 只承载**技术选型**——为某个职位挑一个具体的库、框架、服务、工具或平台。够格写的信号（命中其一即值得写）：

- 引入、更换或淘汰一项技术（如选 ORM、定消息队列、换鉴权方案）；
- 难以逆转——撤销成本超过一个普通迭代；
- 存在多个可行候选且经过真实权衡；
- 未来（包括未来的自己）会问「为什么选它」。

**架构内部的决策不写 ADR**：数据流向、依赖方向、状态归属、模块边界、组件划分是设计判断，没有候选技术可比——写了 ADR 只会把决策记录变成第二份设计文档。它们的家在 design 正文与选型记录（dev_architecture_design）。

跳过的信号还有：沿用既有 ADR 已定的标准、可瞬间逆转的选择、纯外观偏好（归风格规范）。跳过不是不决策，是决策不需要一页纸承载。

## 四问与篇幅

每篇 ADR 回答四个问题：当时的**背景**是什么、**决定**了什么、**考虑过哪些备选**、**后果**是什么。一 ADR 一决策，篇幅以一页为目标——超页通常意味着混入了第二个决策（拆成两篇互链）或 Implementation 细节（留给 design/plan）。

## 各节合格判据

**背景**是全文最重要的节，读者靠它在前提变化后仍能理解决策为何在当时成立。写具体的：数字（端点个数、时延、规模）、硬约束（框架官方语义、许可证、既有约定）、团队因素；选型事实注明查证日期。本决策闭合了旧挂账的，背景第一条把被挂账的事实本身陈述清楚，不引用出处。

**决策**用主动语态写死：「采用 X」「不引入 Y」，不是「考虑 X」「Y 或许可行」。结论之后分条划清边界与分工，每条都是可直接遵守的完整陈述，不指向其他文档。

**备选方案**是长期价值最高的节——半年后有人重提被否的方案时，答案在这里。每个备选三项齐备：优点、缺点、**否决原因**；否决原因要对着本产品上下文说，不是泛泛的「不够好」。一个备选都没写等于宣布「没考虑过别的」。

**后果**是诚实账：正面、负面、风险三段，负面不藏——承认代价才让人信服优点，也提示了何时该重开这个决策。后果里写下「后续可……」就是在给未来的 ADR 挂账，写时即知它会被对照。

## 正文零引用

每篇 ADR 完全自足——正文（含状态行）不出现任何其他 ADR 的编号、文件路径或链接，不设「相关决策」节。引用既有约束时直接陈述约定内容本身（如「schema 从 Drizzle 表结构推导，供 Server Function 入参校验复用」），不写「（约定见 ADR-XXXX）」类指路括号；「承 ADR-XXXX 边界第 N 项」式承接改为把仍有效的边界重写为自己的决策条目。

指路把「现在有效的到底是什么」外包给另一篇文件，读者必须两头对照才能拼出答案，重写一遍才真正自足；决策间的取代、修订关系与导航由 `index.md` 决策日志独家承载。
