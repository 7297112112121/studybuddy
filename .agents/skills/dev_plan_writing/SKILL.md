# 实现计划编写（dev_plan_writing）

## 概述

开发技能组第三步：把已批准的架构设计拆解为**微任务实现计划**。计划写给一个没见过这段对话、但会写地道代码的实现者——他们能做对计划留白处的合理选择，做不对的是你已决定的事：哪些文件、哪些名字与签名、需求里的哪些值、哪些测试证明哪个任务。把这些写下来。

**开始时声明**：「我正在使用 dev_plan_writing 技能为 <特性名> 编写实现计划（档位：轻量/标准/严格）。」

## 流程前后继

上游：dev_architecture_design（已批准的 design 四件套，本技能唯一输入）。下游：dev_implementation（执行已批准的 tasks）。本技能无分支动作——tasks 随 feat 分支落盘，分支收束由下游技能负责。

## 触发范围与档位

**不触发**：spike/原型验证、一次性脚本、纯文档或纯配置变更、不产出产品代码的探索。若不确定，按标准档执行，并在计划头注明档位与理由。

**三档选择**（写入计划头部 `Tier:` 行）：

| 档位         | 适用                               | 必须做                                                        | 可跳过                                    |
| ------------ | ---------------------------------- | ------------------------------------------------------------- | ----------------------------------------- |
| 轻量         | 单文件/低风险/无迁移/无 E2E        | 任务卡（文件+签名+失败测试名+提交信息）、先红后绿、证据汇总行 | design 逐节盘点、Review Focus、子代理纪律 |
| 标准（默认） | 一般特性                           | 完整流程；Review Focus ≤5 条；子代理默认内联                  | —                                         |
| 严格         | 跨模块/迁移/并发/安全敏感/多链并行 | 完整流程 + 全部纪律；Review Focus 可超 5 条但须记裁决         | —                                         |

## 硬门禁（HARD-GATE，对产品代码生效）

**无先失败的测试，即无产品代码。** 单元、集成、E2E、迁移/schema 一律先红后绿；集成与 E2E 是**显式任务**，不是实现后的收尾补写。先写实现再补测试 = 按实现写测试，永远通过但不测边界。

_例外_：触发范围「不触发」的四类不在此列；产品代码路径一旦混入原型，按产品代码处理。

## 保存位置

`docs/dev/AXY-<N>-<slug>/tasks.md`（与 design 同目录；目录名沿用 `docs/product/AXY-<N>-<slug>/` 的编号与 slug，日期写进头部 Date 行）。

## 第 1 步：读 design 并盘点

通读**已批准的 design**（拆分形态：`design.md` 主文件 + `contracts.md` 数据与契约 + `testing.md` 测试接缝 + `adr.md` ADR 关系；旧单文件形态按节名对应同源），逐节盘点为任务原料。**计划信息唯一来源是 design，不回读 proposal**——R / E / AC / 演示态标识符已经 design 的需求承载对照与演示态映射进入 design；design 自查核过一遍，plan 中间再读 proposal = 同一信息重复付费。派生规则：

- **契约表（contracts.md）**：每个契约（签名 + 调用方/被调方 + 错误情形）至少一个任务；错误情形至少一条失败测试，随签名抄入任务卡 Interfaces 行；
- **数据模型与状态转换（contracts.md）**：迁移/schema 任务；每个状态转换至少一个测试任务；
- **UI 与组件**：组件任务；每个演示态至少一个 E2E 任务（任务卡 AC/演示态行必填）；
- **错误与边界（边界表 + E 表映射）**：逐条对应失败测试，呈现位置写进断言；
- **需求承载对照（design.md）与测试接缝（testing.md）**：每个可测接缝至少一个任务，任务卡「失败测试」行取自接缝；
- **范围与非目标**：逐条摘入「不安排任务」清单，执行期不得临时加任务；
- **开放问题**：假设声明进 Global Constraints 或 Review Focus；
- **ADR 关系（adr.md）**：强约束（版本锁定、端点禁用等）进 Global Constraints。

**不得只按需求承载对照的 R 序列拆任务**：design 每条契约、状态转换、错误边界、演示态、可测接缝，都必须有承载任务或明确由哪个任务的哪个测试覆盖。

## 第 2 步：写计划

### 计划结构

按 `templates/tasks.md` 骨架写入：

- **头部**：Goal / Date / Spec / Design / Tier + **Global Constraints**（逐行照抄，值不转述）+ **不安排任务**（design 非目标逐条落名）+ **Review Focus**（默认 ≤5 条，按风险排序；每行必须有测试固定在对应任务）；
- **执行纪律**：全局声明一次 TDD 六步（写失败测试 → 确认失败 → 实现 → 确认通过 → 全量套件 → 提交），任务卡只写差异；
- **执行链节**：按 Consumes / Produces 与文件域划链（划法见下节），子代理打包的依据；
- **裁决记录节**：计划尾部，一行格式，承接执行期偏离。

### 任务依赖与执行链

<合格判据：按任务卡的 Consumes / Produces 与文件域把任务划链，一行一链：链名 + 任务号序列 + 文件域；无依赖的独立任务单列一链。**执行链必须覆盖全部任务**，链间不得共享文件域；链内串行、链间文件域不相交方可并行。单链计划如实写「单链：Task 1→N 串行」，不硬造并行。执行交接的子代理按链打包以此为据，执行期不再现场推链。>

| 链     | 任务序列     | 文件域          | 并行性                |
| ------ | ------------ | --------------- | --------------------- |
| <链名> | Task <a→b→c> | <目录/文件范围> | <可与哪链并行 / 独占> |

### 粒度规则

- **任务**：最小可独立携带一个测试循环、值得一次独立审查的单元。脚手架/配置/文档折叠进需要它的任务；只有审查者可能通过一个任务而否决其邻任务时才拆开。
- **步骤**：以 TDD 六步为准，任务卡只写差异（文件、签名、失败测试、预期失败、提交信息）。
- **硬比例规则**：任务卡正文 ≤15 行（不含模板字段行）；**禁止抄函数体**，签名 + 测试名 + 断言三件套足够。超限须在裁决记录写理由——计划比代码长就是写成了转写。

### 集成与 E2E 任务

单元任务之后安排独立集成/E2E 任务，先红后绿：先写失败用例（对应 design 测试接缝 testing.md 中集成 / E2E 层的接缝），确认失败，再补胶水。禁止「先实现等集成时再补测试」。

### 迁移与 schema 任务

先写「查库断言列/索引不存在」的失败测试并跑红，再写迁移，再跑绿；唯一索引与并发约束用集成测试先红后绿（如并发提交同一手机号仅一次成功）。禁止「先写迁移再补查库断言」——迁移先行则断言永不红，约束等于没测过。

## 第 3 步：机检自查（写完逐项勾选，不勾选不得交审）

- [ ] design 需求承载对照每条 R 能指向任务编号；缺口已补任务
- [ ] 每个契约的错误情形至少一条失败测试，测试名写在任务卡里
- [ ] 每条可测接缝至少一个任务
- [ ] 每个状态转换至少一个测试任务；每个演示态至少一个 E2E 任务
- [ ] 执行链覆盖全部任务，链间无共享文件域（子代理打包以此为准）
- [ ] 「不安排任务」清单与 design 非目标逐条一致，无预留任务
- [ ] 任务卡无函数体、无「处理边界情况」「加适当校验」类空话
- [ ] 跨任务名字/类型与前面任务 Produces 完全一致（`clearLayers()` 不得变 `clearFullLayers()`）
- [ ] Review Focus 每行有测试固定在对应任务，条数符合档位
- [ ] Q 条目无验证任务（测试提质阶段验收）
- [ ] 任务卡正文 ≤15 行/张，超限已记裁决

## 第 4 步：交审与执行交接

计划保存并自查后交人工审阅，批准后触发 **dev_implementation 技能**进入执行——逐任务 TDD 六步、按执行链打包子代理、证据落盘 evidence/、裁决追加等全部执行纪律由该技能承载，本技能不重复。执行中发现计划缺陷时，由 dev_implementation 技能在 tasks.md 裁决记录节追加裁决，不改写本计划已批准的任务卡与上游 design。

## 合理化对照表

| 借口                             | 现实                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------ |
| 「计划这么细了，写代码是抄」     | 计划写过了头。签名 + 测试名 + 断言足够，删函数体                                                 |
| 「对着 proposal 再核一遍才放心」 | design 自查核过一遍。plan 中间再读 = 同一信息重复付费；任务卡有缺口回 design 补，不回读 proposal |
| 「集成测试等写完一起补」         | 补的测试没红过 = 没测过。集成/E2E 是显式任务，先红后绿                                           |
| 「这步太简单，合并描述就行」     | 合并后「可检查的结果」就没了。简单就写短，不写含糊                                               |
| 「小改动也走全套，保险」         | 档位就是为这设的。轻量档保留门禁与任务卡，砍盘点与 Review Focus                                  |
