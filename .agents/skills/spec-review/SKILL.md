# 规范终审（spec-review）

## 概述

开发技能组的收口环节：一个特性实现完成后，**对照 proposal 逐条核对**它是否符合需求规范，同时做代码质量审查。双重判定，两者都通过才算通过：

1. **规范符合性**：proposal 需求条目逐条有实现与测试证据（豁免清单内的除外）；
2. **代码质量**：无引入缺陷、无越界实现（做了非目标里的事）、契约与 design 一致。

## 完成前验证（无新鲜证据不得声称完成）

- 证据必须**当下运行取得**：「刚才跑过了」「实现者说过了」都不算。逐条核对时能重跑的重跑；
- **全量测试套件绿才算绿**：只跑本特性相关文件不算。套件里任何红测试——包括不是你造成的——按名字写进审查报告；看着红测试滚过去而不提 = 隐瞒；
- 「未看着测试失败，即未测过」：核对测试质量时，确认存在「先红后绿」的记录或步骤轨迹（计划中的 Step 2 勾选）；无从确认的测试标记为「证据不足」，不是默认可信。

## 流程

### 1. 读输入

读 proposal 全文（**重点：豁免项表**）、design、实现计划及其裁决记录。豁免清单是判定的分界：清单外缺证据即不通过；清单内的不判失败，但列入报告的「豁免待验清单」供测试提质阶段反查。

### 2. 逐条核对需求条目

对 proposal 每个 R/Q 条目：

| 条目 | 核对内容 | 证据 |
| ---- | ---- | ---- |
| R<n> | 实现落点 + 对应测试存在且通过 | 文件:行号 + 测试命令输出 |
| Q<n>（清单内） | 豁免登记完整（理由/去向/日期） | 豁免表 + 列入豁免待验清单 |

同时核对「非目标」：实现里做了非目标中的事 = 越界，判不通过（除非有裁决记录说明）。

### 3. 代码质量审查

- 契约与 design 签名一致（名字、参数、返回类型）；
- 无未使用的死代码、无绕过契约的直接取数；
- 裁决记录里每条裁决的实现后果已落实。

### 4. 产出审查报告

报告写入 `docs/dev/AXY-<N>-<slug>/review.md`（与该特性的 proposal、design、tasks 同目录），结构：

- **判定**：通过 / 不通过（一句话理由）；
- **逐条核对表**：上表的完整结果；
- **发现清单**：按严重度排序（Critical / Important / Minor），每条含位置与修复建议；
- **豁免待验清单**：移交测试提质的条目原文；
- **证据附录**：运行的命令与输出摘要。

### 5. 出口

不通过的发现只有两个出口：**修复**（修复后重跑对应验证取新证据，再复核）或**豁免登记**（经提出者同意补进 proposal 豁免项表）。「下次再说」「先合了再看」不是出口。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「实现者已经测过了，不用重跑」 | 证据必须新鲜。终审的意义就是不信任转述 |
| 「这条差不多符合」 | 规范符合性没有「差不多」——要么有证据，要么进发现清单 |
| 「测试都在，肯定红绿过」 | 无法确认先红后绿的测试标「证据不足」，不默认可信 |
| 「Minor 就不写了」 | Minor 也是发现。报告失真的方式除了夸大还有漏报 |
| 「这条实现超纲了但写得挺好」 | 越界实现 = 做了非目标的事 = 不通过。好代码也要走变更流程 |

## 产出物

- `docs/dev/AXY-<N>-<slug>/review.md` — 审查报告（判定 + 核对表 + 发现清单 + 豁免待验清单）
