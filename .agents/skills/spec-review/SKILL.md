# 规范终审（spec-review）

## 概述

开发技能组的收口环节：一个特性实现完成后，**对照 proposal 与 design 逐层核对**它是否符合需求规范，同时做代码质量审查。双重判定，两者都通过才算通过：

1. **规范符合性**：四层核对维度全部通过——R 条目、规范细节、design 补强行为、非目标（见流程第 2 步）；Q 条目（性能与质量）整体不进终审，移交测试提质；
2. **代码质量**：无引入缺陷、无越界实现（做了非目标里的事）、契约与 design 一致。

**开始时声明**：「我正在使用 spec-review 技能终审 <特性名> 的实现。」

## 硬门禁（HARD-GATE）

**无新鲜证据不得声称完成：**

- 证据必须**当下运行取得**：「刚才跑过了」「实现者说过了」都不算。逐条核对时能重跑的重跑；
- **全量测试套件绿才算绿**：只跑本特性相关文件不算。套件里任何红测试——包括不是你造成的——按名字写进审查报告；看着红测试滚过去而不提 = 隐瞒；
- 「未看着测试失败，即未测过」：先红后绿按流程第 2 步「先红后绿确认」的方法取证。任务卡的「预期失败」是计划文字，不是运行证据，不构成确认。

**预算门禁：同一 proposal 的全量终审默认至多一次。** 修复后的复审默认轻量——只核对修复点与新增发现，不重开全量逐条核对；「再复核一下」「再看一眼」是轻量复审请求，不构成重开全量的授权；除非人工明确要求，不得自动升级。预算门禁的前提是**首次核对维度完整（四层）**：因漏审导致的复审不是「再复核一下」，按首次核对缺口处理，不适用轻量复审。

## 流程

### 1. 读输入（交接最小集）

按最小集读取，不通读上游全文：

- **proposal（需求规范）**：头部表（状态 / 待确认项）、需求条目表（R，含验收断言列与状态列）、非目标表、边界与约束表、关键决策表（D-xx）、术语与路由及路由行为表、字段与校验规则表（F 表）、错误文案表（E 表）、领域模型（账号与会话状态）、待确认清单（判断有无影响验收的未决项）——Q 条目整体移出终审核对范围，列入报告的「性能与质量移交清单」供测试提质阶段验收，但清单不是原文复制：每条须写验收归属、度量方式与移出依据（D-09）；
- **design（架构设计）**：需求承载对照（含可测接缝列）、契约总表（含错误情形）、数据模型与状态转换、错误边界两张表（边界表 + E 表映射）、测试接缝节、非目标对照、开放问题的假设声明、路由行为落点表；
- **tasks**：Global Constraints、「不安排任务」清单、Review Focus、裁决记录；
- **变更记录（feature-supersede 产出）**：`docs/product/AXY-<N>-<slug>/change-record.md`，存在时必读——特性经历过推翻 / 取代 / 废弃时，它是判断「哪些代码是活的」的依据，墓碑工件以记录为准；不存在时跳过。

逐条核对需要某条 R 的实现细节时，沿需求承载对照表展开 design 对应小节与代码落点；叙述性小节（目标背景、架构总览等）按需再读。design 尚无某补强节（旧模板形态）时，回退 proposal 对应表为核对源，并在报告中注明回退——回退不豁免核对本身。

### 2. 四层核对（逐层取证）

对以下四层逐层取证（核对表结构与列定义见 [templates/review.md](templates/review.md)）：

1. **R 条目层**：proposal 每个 R（状态「废止」的除外）须有实现落点 + 对应测试存在且通过 + **测试断言逐项覆盖 R 的验收断言列**——逐项对照验收断言，不是只看「有测试」；测试通过但断言只盖住验收断言的一部分 = 缺口，在测试质量核对表逐项判。Q 条目不取证；
2. **规范细节层**：F 表逐条规则一致性（规则字符串逐字比对，多输入框共用的规则逐处确认一致）；E 表文案**逐字**比对（逐字，不是「有提示」）与呈现位置一致；路由行为表逐项核对（多分支的逐分支拆行）；D-xx 决策逐条落实（每条决策指认落点与证据，如「协议勾选错误不进汇总计数」「邮箱路径走统一失败文案」）；
3. **design 补强行为层**：design 补强节定义的行为逐项核对——测试接缝每条真实存在且通过；E 表映射的呈现位置与实现一致；状态转换（如会话 有效 / 已撤销 / 已过期）每个转换有测试，**无 R 承载的转换（如「已过期」）在此层兜住**；开放问题按声明的假设实现；路由行为落点表逐项。design 无对应节时回退 proposal 领域模型 / 路由行为表 / E 表，并注明；
4. **非目标层**：非目标逐条核对成表，不得合并为一行「无越界」。核对方法按非目标类型推演（下为示例，按实际非目标类型替换）：表单字段类（如验证码字段隐藏）→ 查表单字段定义；入口不呈现类（如第三方登录、忘记密码）→ 查路由与按钮，决策若要求「代码与测试已删除」则确认删除；纯文本无链接类（如协议名）→ 查文本节点、无 href；插件配置类（如 2FA 未启用）→ 查插件配置；流程无跳转类（如不跳转信息录入页）→ 查登录 / 注册成功路径无该跳转。

**先红后绿确认**（服务以上各层的每个测试证据）：

- 优先采信 tasks 裁决记录或任务卡附带的失败输出——计划要求附带则逐条核对；
- 无附带证据时，对**关键条目抽样**做注入失败验证：临时破坏实现跑红再恢复，或改断言跑红再恢复；抽样至少覆盖每个测试层（单元 / 集成 / E2E）各一条，并覆盖高风险条目（并发唯一性、守卫 / 回退分支、统一失败文案等）；
- 确实无法确认的才标「证据不足」，并**写明尝试过的确认方式**——「证据不足」不得用作批量兜底。

条目较多时可按条目分片派子代理并行取证——prompt 必须自包含：附条目原文、证据要求与输出格式，不依赖本会话上下文；环境不支持子代理时内联执行并明说。**判定与汇总永远由主会话做出**：子代理返回证据，主代理裁定 ✅/❌。

### 3. 代码质量审查

- 契约签名逐条对照 design 契约总表：名字、参数、返回类型逐字一致，标有错误情形的契约错误情形一致（契约一致性核对表承载）；
- 死代码与未使用导出；
- 绕过契约的直接取数；
- console / 调试日志残留；
- 类型逃逸（`any` / 非空断言滥用）；
- 裁决记录每条裁决的实现后果已落实（裁决记录落实核对逐条承载）。

### 4. 产出审查报告

**判定规则**：

- Critical 或 Important 任一 = 不通过；
- 任一 R 判 ❌ 或证据不足 = 不通过；
- 仅 Minor 且规范符合 = 通过并记录（Minor 不阻塞通过）；
- 非目标越界但有裁决记录说明的，核对裁决**先于越界实现做出**（裁决所属任务早于越界落点），成立方可不因该越界判不通过，否则按越界判不通过；
- 状态取值：通过 / 不通过 / 有条件通过（仅 Minor 待修，且已约定期限）。

报告按 [templates/review.md](templates/review.md) 的结构与内联判据写入 `docs/dev/AXY-<N>-<slug>/review.md`（与该特性的 design、tasks 同目录；proposal 位于 `docs/product/AXY-<N>-<slug>/`）：判定、逐条核对表、规范细节核对表、契约一致性核对表、测试质量核对表、非目标逐条表、裁决记录落实核对、发现清单（按严重度排序）、性能与质量移交清单、证据附录——各节的合格判据模板已内联，此处不重复。

### 5. 出口

不通过的发现只有两个出口：**修复**（修复后重跑对应验证取新证据，再复核）或**修订 proposal 回批准门**（经提出者批准）。「下次再说」「先合了再看」不是出口。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「实现者已经测过了，不用重跑」 | 证据必须新鲜。终审的意义就是不信任转述 |
| 「这条差不多符合」 | 规范符合性没有「差不多」——要么有证据，要么进发现清单 |
| 「测试都在，肯定红绿过」 | 先红后绿按方法取证：附带输出 → 抽样注入 → 才允许标证据不足且写明尝试方式 |
| 「无从确认，全标证据不足吧」 | 证据不足须逐条写明尝试过的确认方式；批量兜底 = 没审，关键条目先做注入验证 |
| 「Minor 就不写了」 | Minor 也是发现。报告失真的方式除了夸大还有漏报 |
| 「非目标一行『无越界』就行」 | 非目标逐条成表，每条有核对方法——一行「无越界」审不出越界 |
| 「这条实现超纲了但写得挺好」 | 越界实现 = 做了非目标的事 = 不通过。好代码也要走变更流程 |

## 产出物

- `docs/dev/AXY-<N>-<slug>/review.md` — 审查报告（判定 + 核对表组 + 发现清单 + 性能与质量移交清单 + 证据附录）
