# 规范终审（spec-review）

## 概述

开发技能组的收口环节：一个特性实现完成后，**对照 proposal 逐条核对**它是否符合需求规范，同时做代码质量审查。双重判定，两者都通过才算通过：

1. **规范符合性**：proposal 需求条目逐条有实现与测试证据（豁免清单内的除外）；
2. **代码质量**：无引入缺陷、无越界实现（做了非目标里的事）、契约与 design 一致。

**开始时声明**：「我正在使用 spec-review 技能终审 <特性名> 的实现。」

## 硬门禁（HARD-GATE）

**无新鲜证据不得声称完成：**

- 证据必须**当下运行取得**：「刚才跑过了」「实现者说过了」都不算。逐条核对时能重跑的重跑；
- **全量测试套件绿才算绿**：只跑本特性相关文件不算。套件里任何红测试——包括不是你造成的——按名字写进审查报告；看着红测试滚过去而不提 = 隐瞒；
- 「未看着测试失败，即未测过」：核对测试质量时，确认存在「先红后绿」的轨迹证据（如任务卡「预期失败」所述的失败曾被确认）；无从确认的测试标记为「证据不足」，不是默认可信。

**预算门禁：同一 proposal 的全量终审默认至多一次。** 修复后的复审默认轻量——只核对修复点与新增发现，不重开全量逐条核对；「再复核一下」「再看一眼」是轻量复审请求，不构成重开全量的授权；除非人工明确要求，不得自动升级。

## 流程

### 1. 读输入（交接最小集）

按最小集读取，不通读上游全文：

- **proposal**：头部表、需求条目表、非目标表、边界与约束表、豁免项表——豁免清单是判定的分界：清单外缺证据即不通过；清单内的不判失败，但列入报告的「豁免待验清单」供测试提质阶段反查；
- **design**：需求承载对照表、契约总表；
- **tasks**：Global Constraints、裁决记录。

逐条核对需要某条 R 的实现细节时，沿需求承载对照表展开 design 对应小节与代码落点；叙述性小节（目标背景、架构总览等）按需再读。

### 2. 逐条核对需求条目

对 proposal 每个 R/Q 条目取证（核对表结构与列定义见 [templates/review.md](templates/review.md)）：R 须有实现落点 + 对应测试存在且通过的证据（文件:行号 + 测试命令输出）；Q（清单内）须豁免登记完整（理由/去向/日期）。

条目较多时可按条目分片派子代理并行取证——prompt 必须自包含：附条目原文、证据要求与输出格式，不依赖本会话上下文；环境不支持子代理时内联执行并明说。**判定与汇总永远由主会话做出**：子代理返回证据，主代理裁定 ✅/❌。

同时核对「非目标」：实现里做了非目标中的事 = 越界，判不通过（除非有裁决记录说明）。

### 3. 代码质量审查

- 契约与 design 签名一致（名字、参数、返回类型）；
- 无未使用的死代码、无绕过契约的直接取数；
- 裁决记录里每条裁决的实现后果已落实。

### 4. 产出审查报告

报告按 [templates/review.md](templates/review.md) 的结构与内联判据写入 `docs/dev/AXY-<N>-<slug>/review.md`（与该特性的 proposal、design、tasks 同目录）：判定、逐条核对表、发现清单（按严重度排序）、豁免待验清单、证据附录——各节的合格判据模板已内联，此处不重复。

### 5. 出口

不通过的发现只有两个出口：**修复**（修复后重跑对应验证取新证据，再复核）或**豁免登记**（经提出者同意补进 proposal 豁免项表）。「下次再说」「先合了再看」不是出口。

## 合理化对照表

| 借口 | 现实 |
| --- | --- |
| 「实现者已经测过了，不用重跑」 | 证据必须新鲜。终审的意义就是不信任转述 |
| 「这条差不多符合」 | 规范符合性没有「差不多」——要么有证据，要么进发现清单 |
| 「测试都在，肯定红绿过」 | 无法确认先红后绿的测试标「证据不足」，不默认可信 |
| 「Minor 就不写了」 | Minor 也是发现。报告失真的方式除了夸大还有漏报 |
| 「这条实现超纲了但写得挺好」 | 越界实现 = 做了非目标的事 = 不通过。好代码也要走变更流程 |

## 产出物

- `docs/dev/AXY-<N>-<slug>/review.md` — 审查报告（判定 + 核对表 + 发现清单 + 豁免待验清单）
