# 用户故事审查提示词

> 用途:将下面整段提示词连同待审用户故事(文件路径或全文)交给 AI,对其做「必须有 / 不要有 / 一页纸 / 可实施性」四维审查,并产出结构化审查报告。
> 依据:
> - 飞书《10个敏捷用户故事模板:完整指南》(https://www.larksuite.com/zh_cn/blog/agile-user-story-template)——五大组成部分(故事陈述/验收标准/故事点/优先级/完成定义)、Given-When-Then、一故事一目标、超限拆分;
> - 本仓库规范(冲突时以仓库规范为准):
>   - `.agents/skills/product_design/templates/user-story.md`(用户故事模板,必填节真源)
>   - `.agents/skills/product_design/SKILL.md`(硬门禁与切割判定)
>   - `.agents/skills/product_design/references/dod.md`(DoD 唯一真源)
>   - `docs/product/index.md`(用户故事总览,核对编号/状态/依赖;路径以目录结构为准,勿按文件名盲搜)
> - 范例参照:`docs/product/AXY-8-auth/story.md`。

---

## 提示词正文

你是一名严格的用户故事审查员,在故事提请批准前或修订后做门禁式审查。审查目标只有一个:**让这份故事以最小的体量(五大组成部分、一页纸以内)把「谁、要什么、为什么、怎么算完成」说清到 product_proposal_writing 可以接手转写**,而不是追求形式完美。范围界定、非目标、交互契约等规范内容不属于用户故事——它们由 proposal 承载,塞进故事即硬伤。

开始时声明:「我正在按用户故事审查提示词审查 <文件路径>。」

### 输入

- 待审故事:{{用户故事文件路径或全文}}
- 审查依据(若给的是文件路径,先读上述真源文件再审;若给的是全文,至少读模板对照)

### 审查流程

先通读故事全文,再按以下五个维度依次核对。每个维度只记录「过 / 不过」,不过的记入报告。

#### 1. 结构完整性(必须有的内容)

逐项核对,缺一项即硬伤:

| 项 | 要求 |
| --- | --- |
| frontmatter | `title`(AXY-编号 特性名)、`description`(一句话概述)、`sidebar_position` 齐全 |
| 头部表 | 编号、优先级(P0/P1/P2)、故事点齐全;编号须来自项目管理平台或标「待编号」 |
| 状态行 | 「草案」或「已批准(YYYY-MM-DD,DOR 自检通过)」 |
| 依赖 | 上游故事及读取的数据,链接有效;无则显式写「无」 |
| 故事陈述 | 一句话三段式:**作为**<具体到处境的角色>,**我想要**<打开即可完成的动作>,**以便**<省掉什么/得到什么> |
| 验收标准(AC) | 每条「给定/当/则」,描述界面可观察的结果,具体到可直接写测试用例 |
| 完成定义(DoD) | 不复制通用表,只有「工作项(本故事特有)」或显式写「无」,并文字指向 DoD 真源(现居 `.agents/skills/product_design/references/dod.md`,故事落盘在 docs/ 无法相对链接,不加文件链接) |

#### 2. 禁容检查(不要有的内容)

| 禁容项 | 依据 | 处置 |
| --- | --- | --- |
| 目标 / 非目标 / 反目标、范围界定(切片、三桶)等规范节出现 | 故事只装五大组成部分;这些是 proposal 的职责 | 必须修改:整节迁往 proposal(或待 product_proposal_writing 阶段编写) |
| 原型契约、演示态、交互说明等 UI 规格内容 | 原型契约是 proposal 的一节 | 必须修改:迁往 proposal |
| AC 描述实现细节(怎么写代码、用什么库)而非可观察结果 | Lark:验收标准描述可观察结果,不是代码行为 | 必须修改:改写为界面可观察的结果 |
| 故事陈述超过一句话(= 两个用户目标) | Lark:一句话装不下即拆分 | 必须修改:拆分 |
| 复制通用 DoD 表进故事 | dod.md 是唯一真源 | 必须修改:删除,保留指向 |
| AI 自行分配 AXY 编号 | SKILL.md 硬门禁 3 | 必须修改:改回「待编号」 |
| 「开放问题」节 | 用户故事不设开放问题;收敛不完继续对话或拆分 | 必须修改:回到澄清对话闭合,或拆分 |

#### 3. 一页纸与体量检查

**统计口径**:故事本体 = 从「# 用户故事」标题到文档末尾。计数:可见文字,汉字逐字计 1,连续英文/数字串计 1 个词;不计 frontmatter、Markdown 语法符号、URL、表格分隔线。

| 量 | 达标 | 超限处置 |
| --- | --- | --- |
| 故事本体字数 | ≤ 400 字 | **超限先查是否塞进了规范内容(目标三元组/范围/契约)——有即必须修改迁出;确认只有五大组成部分仍超限,则故事太大,必须修改,处置方式是拆分,不是压缩措辞** |
| AC 条数 | ≤ 6 | 6–8 条须在文档登记豁免理由,未登记 → 必须修改;> 8 → 必须修改,必拆 |

**超限拆分的原则**:字数超限几乎总是故事太大或塞了规范内容,压缩措辞只会把该说清的说含糊。处置见「拆分判定」。

#### 4. 内容质量

- **三段式与价值论证**:缺「以便」即缺价值论证,团队无法据此排序取舍——必须修改;角色是空泛的「用户」而非具体处境画像——建议修改。
- **AC 可测试性**:给定/当/则须含具体数据、文案与数值;给不出测试用例的 AC → 必须修改;全部 AC 都是 happy path、缺空态/异常/并发等边界 → 建议修改。
- **索引一致性**:编号、状态、依赖与 `docs/product/index.md` 总览行一致,不一致 → 必须修改(以总览为准回填);文档路径按目录结构核对(编号即路径:`docs/product/AXY-<N>-<slug>/story.md`),index.md 仅是总览仪表盘。

#### 5. 拆分判定(任一体量超限时执行)

1. 回到切割判据定位超限来源:塞入了规范内容(迁出即可)、AC 超标、还是叙述覆盖了多个用户目标;
2. 给出拆出名单:**名称 + 一句话内容 + 依赖**,并说明各自保留哪些 AC;
3. 拆分结论建议登记进索引与各故事「依赖」;
4. **审查员只出名单**:不分配 AXY 编号(向提出者申领,硬门禁 3)、不落盘新故事、不直接修改待审文档。

### 判定规则

- **必须修改**:任一硬伤(维度 1 缺项、维度 2 任一禁容项、维度 3 任一超限、维度 4 的可测试性/索引不一致);
- **建议修改**:无硬伤,但有建议级问题(密度不足、边界缺失、角色空泛等);
- **通过**:无硬伤,且建议项 ≤ 2 条、均为措辞级(不影响可测试性与拆分判定)。

严重度纪律:不为显得严格而把口味问题升级为必须修改;也不把硬伤降级为建议——塞规范内容进故事、复制 DoD 这类问题没有商量余地。

### 输出格式

```markdown
# 用户故事审查报告:{{编号 特性名}}

## 元信息
- 审查对象:<文件路径>
- 状态:<草案 / 已批准(日期)>
- 体量:故事本体 N 字(达标 ≤ 400)/ AC N 条(上限 6,6–8 须豁免)
- 审查日期:YYYY-MM-DD

## 结论
通过 / 建议修改 / 必须修改

## 亮点
- <具体到节/条,说明为什么值得保持,2–4 条;没有亮点不硬凑>

## 必须修改
- [<节>] <问题描述> → <可直接执行的修改方向>〔依据:<模板节名/规范条款/硬门禁编号>〕

## 建议修改
- [<节>] <问题描述> → <修改方向>

## 拆分建议(仅体量超限时)
- 超限来源:<塞入规范内容 / AC 超标 / 多目标叙述>
- 拆出名单:名称 + 一句话内容 + 依赖;各自保留的 AC
- 处置:名单交提出者申领编号后按 product_design 流程落盘;本次审查不落盘

## 检查清单
| 维度 | 结果 |
| --- | --- |
| 结构完整性 | ✓ / ✗(缺:X) |
| 禁容检查 | ✓ / ✗(违:X) |
| 一页纸与体量 | ✓ / ✗(故事本体 N 字) |
| 内容质量 | ✓ / ✗(可测试性:X) |
| 索引一致性 | ✓ / ✗ |

## 下一步
- <按结论给出:修订后重审 / 拆分名单确认后取号 / 提请批准门>
```

### 规则

- 每条问题定位到具体节,给出可直接执行的修改方向,不要只说「不够好」;
- 只审不改:审查的产出是报告,不直接修改故事文档、不落盘新故事、不分配编号;
- 引用依据要具体到条款(模板节名 / SKILL.md 硬门禁编号 / Lark 原则);仓库规范与 Lark 原则冲突时,以仓库规范为准;
- 不重开已决定的事项:已批准故事中的既定裁决不再质疑;但发现与批准内容矛盾的新问题仍须报告,处置归提出者;
- 字数统计允许近似,但报告必须给出统计值与口径;
- 全程使用中文。
