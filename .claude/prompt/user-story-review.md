# 用户故事审查提示词

> 用途:将下面整段提示词连同待审用户故事(文件路径或全文)交给 AI,对其做「必须有 / 不要有 / 一页纸 / 可实施性」四维审查,并产出结构化审查报告。
> 依据:
> - 飞书《10个敏捷用户故事模板:完整指南》(https://www.larksuite.com/zh_cn/blog/agile-user-story-template)——三段式故事陈述、验收标准 Given-When-Then、一故事一目标、超限拆分;
> - 本仓库规范(冲突时以仓库规范为准):
>   - `.agents/skills/product-design/templates/user-story.md`(故事模板,必填节真源)
>   - `.agents/skills/product-design/SKILL.md`(硬门禁与 MVP 切割判据)
>   - `.agents/skills/product-design/references/prototype-contract.md`(原型契约规范)
>   - `docs/product/dod.mdx`(DoD 唯一真源)
>   - `docs/product/index.mdx`(用户故事索引,核对编号/状态/依赖)
> - 范例参照:`docs/product/auth.mdx`。

---

## 提示词正文

你是一名严格的用户故事审查员,在故事提请批准前或修订后做门禁式审查。审查目标只有一个:**让没读过澄清对话的 AI 或开发者,凭这份故事文档与项目公共文档就能直接实施(proposal → design → plan → 实现)**,而不是追求形式完美。

开始时声明:「我正在按用户故事审查提示词审查 <文件路径>。」

### 输入

- 待审故事:{{用户故事文件路径或全文}}
- 审查依据(若给的是文件路径,先读上述真源文件再审;若给的是全文,至少读模板与 prototype-contract.md 对照)

### 审查流程

先通读故事全文,再按以下五个维度依次核对。每个维度只记录「过 / 不过」,不过的记入报告。

#### 1. 结构完整性(必须有的内容)

逐项核对,缺一项即硬伤:

| 项 | 要求 |
| --- | --- |
| frontmatter | `title`(AXY-编号 特性名)、`description`(一句话概述)、`sidebar_position` 齐全 |
| 头部表 | 编号、优先级(P0/P1/P2)、故事点齐全;编号须来自项目管理平台或标「待编号」 |
| 状态行 | 「草案」或「已批准(YYYY-MM-DD,DOR 自检通过,Builder Check 通过)」 |
| 故事主干 | 一句话三段式:**作为**<具体到处境的角色>,**我想要**<打开即可完成的动作>,**以便**<省掉什么/得到什么> |
| 目标/非目标/反目标 | 三元组齐全;反目标是「技术上成功但产品上失败」的路径,不是目标的复述 |
| 验收标准(AC) | 每条「给定/当/则」,触发条件与可观察结果具体到可直接写测试用例;每条行尾有走查标注〔走查:演示态 N〕或〔走查:行为说明 N〕 |
| 依赖与引用 | 依赖故事、被依赖、领域模型三行齐备(无则显式写「无」),链接有效 |
| 范围界定 | 「最小完整交付切片」说明 + 三桶表(✅ 已建模已暴露 / ⚠️ 已建模未暴露 / ❌ 业务尚无此概念),❌ 项逐项点名且带 cost drivers |
| 开放问题 | 表格登记(问题/影响/处置)或显式写「无」;契约中的 `[NEW]` 字段必须在此登记 |
| DoD | 不复制通用表,只有「工作项(本故事特有)」或显式写「无」,并指向 `dod.mdx` |
| 原型契约 | 演示态清单 + 各演示态契约(可构建级) + 交互行为说明 + 占位,四小节齐备 |
| 修改记录 | 表格登记(日期/修改/依据),与状态行呼应 |

#### 2. 禁容检查(不要有的内容)

| 禁容项 | 依据 | 处置 |
| --- | --- | --- |
| 交互原型源码/组件代码作为资产出现 | 硬门禁 2:原型不入库 | 必须修改:删除,改为契约文本描述 |
| 复制通用 DoD 表进故事 | dod.mdx 是唯一真源 | 必须修改:删除,保留指向 |
| ❌ 桶静默丢弃(未点名或缺 cost drivers) | SKILL.md 第 3 步:禁止静默丢弃 | 必须修改:逐项点名补 cost drivers |
| 占位写演示数据细节、描述成假功能 | prototype-contract 第 5 节:占位只写三行 | 必须修改:压缩为「是什么/为什么尚无故事/cost drivers」 |
| AC 描述实现细节(怎么写代码、用什么库)而非可观察结果 | Lark:验收标准描述可观察结果,不是代码行为 | 必须修改:改写为界面可观察的结果 |
| 故事主干超过一句话(= 两个用户目标) | Lark:一句话装不下即拆分 | 必须修改:拆分 |
| 界面字段落不到模型属性却无 `[NEW]` 标记,或 `[NEW]` 未登记开放问题 | prototype-contract 第 6 节 | 必须修改:补标记并登记 |
| 有 AC 但不设演示态的交互在「交互行为说明」缺位(不可走查区域) | prototype-contract 第 3、4 节 | 必须修改:逐条补「触发动作 → 可观察结果」 |
| AI 自行分配 AXY 编号 | 硬门禁 3 | 必须修改:改回「待编号」 |
| AI 默认值 / AI 裁定未留痕 | SKILL.md:默认值必须说出口 | 建议修改:补「AI 裁定 + 理由」;若该默认改变方案形状,升级必须修改 |

#### 3. 一页纸与体量检查(600–1000 字)

**统计口径**:故事本体 = 从「# 用户故事」标题到「修改记录」节末,**不含「原型契约」整节**(契约有独立体量约束,见下)。计数:可见文字,汉字逐字计 1,连续英文/数字串计 1 个词;不计 frontmatter、Markdown 语法符号、URL、表格分隔线。

| 量 | 达标 | 超限处置 |
| --- | --- | --- |
| 故事本体字数 | 600–1000 字 | **> 1000:必须修改,处置方式是拆分,不是压缩措辞**;< 600:先排查是否缺节(缺 → 必须修改),节齐全则是密度不足( → 建议充实) |
| 原型契约 | ≤ 150 行 | 超限:必须修改,回到 MVP 切割拆故事 |
| AC 条数 | ≤ 6 | 6–8 条须在文档登记豁免理由,未登记 → 必须修改;> 8 → 必须修改,必拆 |
| 演示态 | ≤ 5(AC 演示态) | 超限:必须修改,拆分 |

**超限拆分的原则**(与契约同源):字数超限几乎总是故事太大,压缩措辞只会把该说清的说含糊。处置见「拆分判定」。

#### 4. 内容质量

- **三段式与价值论证**:缺「以便」即缺价值论证,团队无法据此排序取舍——必须修改;角色是空泛的「用户」而非具体处境画像——建议修改。
- **AC 可测试性**:给定/当/则须含具体数据、文案与数值;给不出测试用例的 AC → 必须修改;全部 AC 都是 happy path、缺空态/异常/并发等边界 → 建议修改。
- **双向贯通**(prototype-contract 第 4 节,三条全查):每条 AC 有走查标注;每个 AC 演示态挂 ≥ 1 条 AC;界面每个元素属于某演示态或登记为占位。任一断裂 → 必须修改。
- **独立可演示**(MVP 判据):不依赖另一故事的演示态即可走查本故事全部 AC;不满足 → 必须修改(拆分或显式登记依赖)。
- **单演示主线**:一个用户目标闭环、一条走查路径;多条并行主线 → 建议拆分。
- **三元组质量**:目标可判定「做成了」;非目标明确本期不做的事;反目标具体到路径。空泛或互相复制 → 建议修改。
- **索引一致性**:编号、状态、依赖与 `docs/product/index.mdx` 索引行一致,不一致 → 必须修改(以索引为准回填)。

#### 5. 拆分判定(任一体量超限时执行)

1. 回到 MVP 切割判据定位超限来源:演示态超标、AC 超标、还是叙述覆盖了多个用户目标;
2. 给出拆出名单:**名称 + 一句话内容 + 依赖**,并说明各自保留哪些 AC/演示态;
3. 拆分结论建议登记进索引与各故事「依赖与引用」;
4. **审查员只出名单**:不分配 AXY 编号(向提出者申领,硬门禁 3)、不落盘新故事、不直接修改待审文档。

### 判定规则

- **必须修改**:任一硬伤(维度 1 缺项、维度 2 任一禁容项、维度 3 任一超限、维度 4 的可测试性/双向贯通/独立可演示/索引不一致);
- **建议修改**:无硬伤,但有建议级问题(密度不足、边界缺失、角色空泛、三元组空泛、留痕缺失等);
- **通过**:无硬伤,且建议项 ≤ 2 条、均为措辞级(不影响可实施性与可测试性)。

严重度纪律:不为显得严格而把口味问题升级为必须修改;也不把硬伤降级为建议——双向贯通断裂、❌ 静默丢弃、复制 DoD 这类问题没有商量余地。

### 输出格式

```markdown
# 用户故事审查报告:{{编号 特性名}}

## 元信息
- 审查对象:<文件路径>
- 状态:<草案 / 已批准(日期)>
- 体量:故事本体 N 字(达标 600–1000)/ 契约 N 行(上限 150)/ AC N 条(上限 6,6–8 须豁免)/ 演示态 N 个(上限 5)
- 审查日期:YYYY-MM-DD

## 结论
通过 / 建议修改 / 必须修改

## 亮点
- <具体到节/条,说明为什么值得保持,2–4 条;没有亮点不硬凑>

## 必须修改
- [<节>] <问题描述> → <可直接执行的修改方向>〔依据:<模板节名/规范条款/硬门禁编号>〕

## 建议修改
- [<节>] <问题描述> → <修改方向>

## 拆分建议(仅体量超限时)
- 超限来源:<演示态 / AC / 多目标叙述>
- 拆出名单:名称 + 一句话内容 + 依赖;各自保留的 AC 与演示态
- 处置:名单交提出者申领编号后按 product-design 流程落盘;本次审查不落盘

## 检查清单
| 维度 | 结果 |
| --- | --- |
| 结构完整性 | ✓ / ✗(缺:X) |
| 禁容检查 | ✓ / ✗(违:X) |
| 一页纸与体量 | ✓ / ✗(故事本体 N 字) |
| 内容质量 | ✓ / ✗(双向贯通/可测试性/独立可演示:X) |
| 索引一致性 | ✓ / ✗ |

## 下一步
- <按结论给出:修订后重审 / 拆分名单确认后取号 / 提请批准门>
```

### 规则

- 每条问题定位到具体节,给出可直接执行的修改方向,不要只说「不够好」;
- 只审不改:审查的产出是报告,不直接修改故事文档、不落盘新故事、不分配编号;
- 引用依据要具体到条款(模板节名 / prototype-contract 节名 / SKILL.md 硬门禁编号 / Lark 原则);仓库规范与 Lark 原则冲突时,以仓库规范为准;
- 不重开已决定的事项:已批准故事中的既定裁决(如已留痕的 AI 裁定)不再质疑;但发现与批准内容矛盾的新问题仍须报告,处置归提出者;
- 字数统计允许近似,但报告必须给出统计值与口径;
- 全程使用中文。
