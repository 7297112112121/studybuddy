# 研发流程

研发流程分三大部分——产品设计、开发落地、测试提质——分别由 `.agents/skills/` 下的技能组承载，技能间靠「引用上游已批准文档」强制接力。本文件是流程总览，各技能细节见其 SKILL.md。

## 总流程

```text
模糊想法 → [product-design] → 用户故事
         → [proposal-writing] → proposal（批准门一）
         → [architecture-design] → design（批准门二）
         → [plan-writing] → 实现计划
         → TDD 实现（含集成 / E2E 测试）
         → [spec-review] → 审查报告（豁免项移交测试提质）
```

## 产品技能组（product/）

- product-design 把未经结构化的想法经苏格拉底式提问澄清为落盘用户故事（docs/product 文档 + 交互原型 + 索引登记）。
- 用户故事未经人工批准不得进入开发落地，这是产品与开发两组之间的硬门禁。
- 纯技术决策不走本组，改走 ADR 流程。

## 开发技能组（development/）

- proposal-writing 把已批准用户故事转写为需求规范，一个特性一份，含编号需求条目、非目标、性能指标与豁免清单。
- proposal 未获人工批准，不得做架构设计、拆任务或写任何产品代码（批准门一）。
- architecture-design 把 proposal 转化为架构设计，数据模型精确到可建表、契约精确到签名级别。
- 技术选择须与既有 ADR 及代码目录约定核对，冲突或无覆盖时先走 ADR 流程再回来设计。
- design 未获人工批准，不得拆分任务或写任何产品代码（批准门二）。
- plan-writing 把 design 拆为微任务实现计划，含 Global Constraints、Review Focus 与任务间 Interfaces 块。
- 一切产品代码遵循 TDD 铁律：无先失败的测试即无产品代码，集成与 E2E 是显式任务而非收尾补写。
- 执行中发现的计划缺陷记入「裁决记录」节，不停摆等人。
- spec-review 在实现全部完成后对照 proposal 逐条核对，双重判定规范符合性与代码质量。
- 证据必须当下运行取得，全量测试套件绿才算绿，无法确认先红后绿的测试标「证据不足」。
- 审查报告给出判定、核对表、发现清单与豁免待验清单，不通过的发现只有修复或豁免登记两个出口。

## 测试技能组（暂缺）

- 承接 spec-review 的豁免待验清单，在测试提质阶段完成质量加固，现阶段暂不编写。
