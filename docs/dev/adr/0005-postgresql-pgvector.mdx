# ADR-0005：数据库采用 PostgreSQL 17 + pgvector

## 状态

已接受（Accepted）

## 日期

2026-11-12

## 背景

- 数据面有三类需求：结构化业务数据（用户、学业规划、任务、情绪记录、练习题）、向量检索（学习资料 RAG、长期记忆）、以及未来的混合检索（关键词 + 语义）。
- 产品边界决定数据只来自自有系统，无需多源联邦；部署基线为 Docker 自托管（ADR-0001），团队希望最小化有状态组件数。
- 当前规模为单校学生量级，向量数据量预计在万级到十万级。

## 决策

PostgreSQL 17 作为唯一持久化主库；启用 pgvector 扩展承担向量存储与检索（HNSW 索引）；不引入独立向量数据库。中文全文检索先以「应用侧分词 + tsvector」方案落地，效果不足时再评估 zhparser / pgroonga。版本说明：PostgreSQL 18 已 GA，若部署时镜像或托管平台无版本约束，可评估直接采用 18；本 ADR 的决策基准为 17。

## 备选方案

### MySQL 8
- 优点：运维熟悉度高，资料多。
- 缺点：无原生向量类型与索引，RAG 需外挂组件。
- 否决原因：核心需求（向量检索）缺失。

### 关系库 + 独立向量库（Qdrant / Milvus）
- 优点：向量检索性能与功能上限更高（量化、稀疏向量、混合检索）。
- 缺点：多一个有状态组件；学习资料更新/删除时跨库一致性（元数据与向量同步）需要自管。
- 否决原因：当前规模远未触及 pgvector 上限；若未来检索规模进入百万级，以新 ADR 取代本条。

### SQLite（含 libsql）
- 优点：零运维，单文件备份。
- 缺点：并发写能力、扩展生态（向量、全文、JSON）与长期演进弱于 PostgreSQL。
- 否决原因：多用户在线服务的写并发预期不符合 SQLite 定位。

## 后果

### 正面
- 一个库覆盖「关系 + 向量 + 全文 + JSON」。
- 向量与业务数据同事务一致：资料更新与向量更新在同一事务提交，天然避免「库里有、索引里没有」。
- 备份、监控、连接池都只有一套。

### 负面
- pgvector 的 HNSW 索引内存占用与召回率需要调参经验（参数随数据分布变化）。
- 中文全文检索需要额外工程（分词预处理或插件）。
- PostgreSQL 大版本升级在自托管下需要停机窗口。

### 风险
- 团队 PG 调优经验有限：上线前建立慢查询日志与连接池基线（框架层池化起步），避免连接数事故。
