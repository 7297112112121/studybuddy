# ADR-0035：服务端日志采用 pino

## 状态

已接受（Accepted）

## 日期

2026-11-25

## 背景

- 异常体系确立「技术报错归一前必须留痕」纪律（见[异常处理纪律](../异常处理纪律.md)），需要服务端结构化日志载体；现状服务端零日志，统一接口归一兜底码时原始异常直接丢弃，生产故障不可回溯。
- 部署形态为 Docker Compose 单机自托管，日志消费面是容器 stdout，无需自建日志存储。
- RSC 未捕获异常由 Next 自带服务端日志（digest 关联）覆盖，需补的是统一接口契约切面归一点与适配点的主动留痕。

## 决策

服务端日志采用 pino：

1. 载体唯一：服务端留痕一律经 `src/common/logger.ts` 的 pino 单例，JSON 行写 stdout，级别经 `LOG_LEVEL` 环境变量调节；
2. 不启用 transport 与 pino-pretty：pretty 输出经 worker 线程实现，与打包器组合存在运行时风险；本地开发需要可读格式时以管道 `| pino-pretty` 处理，pino-pretty 不进生产依赖；
3. 留痕点只限异常处理纪律定义的归一点与适配点，业务报错不留痕；
4. 浏览器不引入 pino：客户端留痕（渲染边界、适配器）仍用 console.error；
5. 未捕获异常不重复接：Next 对 RSC 渲染异常自带服务端日志与 digest，边界组件只做 console.error。

## 备选方案

### console 直用

- 优点：零依赖。
- 缺点：无级别、无结构化、无统一序列化，留痕纪律没有可信载体，排障靠肉眼扫文本。
- 否决原因：留痕是异常体系的强制环节，需要结构与级别保证。

### winston

- 优点：老牌通用，传输器生态丰富。
- 缺点：性能弱于 pino，API 形态旧式，维护活跃度下降。
- 否决原因：stdout JSON 场景下 pino 以更低开销覆盖同等能力。

### Sentry 等观测平台

- 优点：告警、聚合、堆栈还原开箱即用。
- 缺点：引入外部服务依赖与成本，超出现阶段单机自托管规模；SDK 接入需扩大部署面。
- 否决原因：当前诉求是「异常可回溯」，结构化 stdout 已满足；观测平台留待真实排障需求出现再立项。

## 后果

### 正面

- 归一兜底码时可回溯原始异常：异常对象与方向随 JSON 行落 stdout，容器日志管道可直接消费。
- pino 零配置即用，调用面收敛在 `src/common/logger.ts` 单例。

### 负面

- 本地开发读 stdout JSON 不如文本直观，需自行管道 pino-pretty。
- pino 为 CommonJS 包，经 Next 打包器处理需构建验证；若打包异常，以 serverExternalPackages 外部化兜底。

### 风险

- 日志只落 stdout 无持久化，容器重启后历史丢失；需要检索时再评估日志收集方案。
