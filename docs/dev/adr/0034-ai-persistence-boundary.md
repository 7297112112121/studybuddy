# ADR-0034：AI 服务持久化边界收敛

## 状态

已接受（Accepted）

## 日期

2026-11-24

## 背景

- AI 服务形态已定：python 侧以 AgentScope 2.0 承载 Agent 能力（推理循环、工具、记忆计算、RAG 计算），Next 承载 SSE 加工与下发；两服务同一 Docker Compose 编排，python 仅内网可达。
- 原方案中记忆（mem0）的向量库与 history 由 python 侧直连自有 PostgreSQL：python 服务持有数据库连接即持有持久化能力，持久化逻辑分裂在两个服务，数据写入路径无法单一收拢，数据所有权随 schema 演进漂移。
- 开发者裁定单一流约束延伸至 AI 链路：Next 全栈定位为 BFF——发送请求数据处理、响应数据处理与持久化；python 服务定位为能力计算引擎，不涉及持久化服务能力。AI 复杂实现不自建的判断不变：把 server 层承担的 AI 服务外包给成熟框架所在的 python 服务。

## 决策

python AI 服务无持久层，持久化归 Next：

1. python 服务不直连 PostgreSQL 与 Redis，不持有任何数据库连接、驱动或连接池；
2. AI 链路产生的数据（会话、消息、记忆、RAG 语料）持久化一律经 Next 内网 API 落业务逻辑层（queries/service）写入自有 PostgreSQL；
3. python 侧记忆与 RAG 计算所需的历史与向量数据经同一内网 API 通道读写；mem0 仍为记忆计算引擎（经框架内建中间件承载），其存储后端以 Next 内网 API 适配承载，记忆数据最终落自有 PostgreSQL pgvector；
4. 记忆表结构归属（mem0 自管或进业务迁移体系）由承载 AI 会话能力的特性设计裁定；
5. embedding 与模型凭据仍经环境变量注入 python 服务，不在代码中硬编码。

## 备选方案

### 维持 python 直连数据库（mem0 官方 pgvector 后端直落）

- 优点：mem0 官方维护 pgvector 后端，开箱即用，零适配代码。
- 缺点：持久化路径分裂在两个服务，写入无单一收拢点；python 服务具备 schema 变更能力，数据所有权漂移。
- 否决原因：与单一流约束冲突——持久化必须唯一归口 Next 业务逻辑层。

### python 自持本地文件态/内嵌存储

- 优点：python 侧自洽，无跨服务存取往返。
- 缺点：多副本部署不一致、不可 SQL 查询、需要独立于数据库的备份面。
- 否决原因：与记忆方案既定硬约束（多副本一致、SQL 可查、不新增备份面）全部冲突。

## 后果

### 正面

- 持久化单一归口：全部写入经业务逻辑层，校验、审计与迁移体系单点收拢。
- python 服务无状态化更彻底，镜像与扩缩容不携带数据面。

### 负面

- mem0 官方 pgvector 后端不能直接使用，需实现经 Next 内网 API 的存储适配层，是新增的自维护代码。
- AI 链路每一次记忆读写多一跳内网 HTTP，时延与故障面增加。

### 风险

- 存储适配层对 mem0 所需向量检索算子的语义覆盖面需在特性设计期核对，适配不全将限制记忆检索能力。
