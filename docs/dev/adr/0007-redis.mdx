# ADR-0007：缓存与临时态采用 Redis

## 状态

已接受（Accepted，带引入时机约束）

## 日期

2026-11-12

## 背景

- 三类现实需求已可预见：
  1. AI 对话的会话上下文与流式输出中间态缓存；
  2. 接口限流——Next.js 官方 BFF 指南明确：多实例部署下进程内限流计数不可靠，需要共享存储；
  3. 产品「动态任务调度」方向需要定时与队列基元。
- 当前 0.1.0 计划单实例 Docker 部署，但多实例是可预期的演进方向。

## 决策

引入 Redis 7+ 作为「可丢失数据」专用组件：限流计数、AI 会话上下文缓存、一次性 token、轻量队列（BullMQ）。客户端用 ioredis。**纪律：Redis 只允许存放可重建或可过期的数据，持久化事实一律以 PostgreSQL 为准。**部署初期与主应用同 compose 编排；设置内存上限与淘汰策略，队列所在逻辑 db 关闭淘汰（或独立实例），避免任务被缓存淘汰策略清掉。

**引入时机**：不与第一个功能迭代强制绑定，在「限流」或「AI 会话上下文缓存」任一需求落地时引入。

## 备选方案

### 不引入 Redis（Next.js 缓存 + 进程内 LRU + PG 表限流）
- 优点：组件最少，运维最简，单实例下完全够用。
- 缺点：限流退化为单实例语义；队列需自建表轮询方案；AI 上下文缓存落库增加 PostgreSQL 读写与清理负担。
- 否决原因：三类需求叠加后，自建方案的复杂度反而高于引入一个成熟组件；且多实例演进时全部要重写。

### Upstash / 云托管 Redis
- 优点：免运维，按请求计费，Serverless 场景友好。
- 缺点：自托管场景下徒增网络延迟与供应商依赖。
- 否决原因：部署基线是自托管（ADR-0001）；未来若迁移 Serverless 平台可重新评估。

### Memcached
- 优点：纯缓存场景简单可靠。
- 缺点：无持久化选项，无队列与丰富数据结构。
- 否决原因：队列与任务调度需求超出其能力边界。

## 后果

### 正面
- 限流、缓存、队列三类需求共享一套基础设施。
- 为多实例水平扩展预留正确语义（计数共享、分布式锁可用）。

### 负面
- 新增一个有状态组件的运维面：持久化策略、内存水位、监控。
- 本地开发环境需要 compose 拉起 Redis。

### 风险
- 最大风险是被当作持久存储误用（纪律见决策）；BullMQ 任务需要失败重试与死信处理的约定。
- AI 会话上下文缓存需设计 key 过期与容量上限，防止长会话撑爆内存。
