# ADR-0010：国际化方案采用 next-intl

## 状态

已接受（Accepted）——最终决策偏离了最初的 react-i18next 提案，改用 next-intl。

## 日期

2026-11-12

## 背景

- 产品当前唯一目标语言是 zh-CN（面向国内本科生），但海外版/双语界面是可见的演进方向。
- 界面文案目前散落在组件内，缺乏集中管理，无论最终选什么方案，「文案集中」都应先做。
- Next.js 官方 i18n 指南的推荐路径是「`[lang]` 路由段 + 服务端词典 + proxy 语言协商」，其推荐资源列表包含 next-intl 等，**不含 react-i18next**；指南同时提供 `next/root-params` 让深层服务端组件免传参读取语言。
- 既定提案为 react-i18next。

## 决策

采用 **next-intl**：RSC 原生支持（服务端与客户端组件同一套 API 心智），支持**无路由前缀策略**——单语言阶段不强制 `/zh` 前缀，既有 URL 与 SEO 不受扰动；文案以 JSON 命名空间管理。语言协商先用 cookie / Accept-Language（proxy 中实现），未来需要 SEO 级多语言时再迁移到 `[lang]` 前缀路由（届时以新 ADR 取代本条的路由部分）。

## 备选方案

### react-i18next（既定提案）
- 优点：i18next 是事实标准，插值/复数/ICU 能力成熟；框架无关；生态与社区最大；团队若已有 i18next 经验则上手最快。
- 缺点：客户端优先的设计，在 RSC 架构下需要自行拼装服务端初始化（resources-to-backend、getFixedT 等约定），与 App Router 的集成是「适配」而非「原生」；包体积更大；Next 官方 i18n 指南未将其列入推荐资源。
- 保留意见：可行，但长期维护面更大。若团队确实已有 i18next 积累且界面完全客户端化，可作为接受本方案的替代选择。

### 暂不引入 i18n 框架（自建 zh 字典模块）
- 优点：零依赖，最快。
- 缺点：丢失插值/复数/命名空间能力，未来引入框架时逐文件返工。
- 否决原因：与「保留国际化能力」的产品预期矛盾。

## 后果

### 正面
- 服务端与客户端统一 API，与 RSC 架构零摩擦。
- 单语言阶段 URL 不变，无路由前缀迁移成本。
- 文案集中后可直接对接翻译流程。

### 负面
- 绑定 Next 生态，与 i18next 标准不互通；若未来脱离 Next 需要整体替换。
- 版本与 Next.js 大版本的兼容需要验证：升级 Next 前先查兼容矩阵。

### 风险
- 无前缀策略下语言依赖 cookie，CDN/缓存键必须包含语言维度，避免「串语言缓存」。
