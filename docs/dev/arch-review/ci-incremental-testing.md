# 架构评审：CI 测试策略——增量筛选的引入时机

状态：**草案**

- 评审日期：2026-11-23
- 触发背景：开发者痛点——「CI/CD 无论新功能还是小修改都走全量测试兜底」，提议「默认增量测试（按文件/模块变更筛选），全量作兜底」。
- 评审范围：`.github/workflows/ci.yml` 校验链的测试步骤（单测 / 集成 / E2E）与既有裁剪机制（ADR-0026）；deploy.yml 不含测试步骤，不在范围内。

## 盘点事实（证据）

- 实测一次代码变更的全量 verify（run 44913469940，冷缓存）：总 4m47s，构成——依赖安装 1m17s（仅 lockfile 变更时发生）、容器启动 17s、format/lint/type-check 12s、Build 15s、**单测 11s**、**集成测试 3s**、Playwright 安装 15s、**E2E 1m52s**（含 webServer 二次 build + start）。
- **测试本体全量成本 = 14 秒**（单测 + 集成），占 verify 不到 5%；E2E 是最大单项（约 40%）。
- E2E 为冒烟规模：31 用例（auth 13 / calendar 17 / homepage 1），已按模块分文件（`e2e/auth.spec.ts` 等）。
- 测试文件已按模块分轨（`tests/<模块>/**`、`tests/integration/<模块>/**`），与 `docs/dev/代码目录.md` 的模块边界一致——增量化在结构上无障碍，纯粹是值不值的问题。
- ADR-0026 已确立兜底式裁剪框架（changes 作业 + job 级 if + paths-filter 单源），原则「宁漏跳、不漏跑」；docs-only PR 已秒级跳过。

## 风险清单

| # | 风险陈述 | 证据 | 影响面 |
| --- | --- | --- | --- |
| R1 | 「全量测试兜底」的实际成本被高估：增量筛选单测/集成的收益上限仅 14s/PR，不抵影响面映射维护（lib/db/components/i18n 为共享层，变更须全跑）与漏测风险；增量方向与 ADR-0026 兜底原则相反 | run 44913469940 步骤耗时 | 现阶段无实际痛感——痛点经实测不成立为结构性风险 |
| R2 | E2E 无差别全跑是 verify 最大单项（1m52s），但冒烟规模下按模块裁剪仅省 20–40s/单模块 PR——webServer 的 build + start 为固定开销，裁用例省不掉 | `e2e/*.spec.ts` 用例分布 + 步骤耗时 | 每 PR 反馈中约 40% 来自此项，但可裁部分有限 |

## 裁决记录

### 裁决 1：单测/集成是否引入按变更的增量筛选

| 候选 | 方案 | 理由 / 风险 |
| --- | --- | --- |
| A1 不引入（**已裁定**） | 单测/集成维持全量 | 实测 14s，收益不抵维护与漏测风险；符合「只设计足够当前需求的架构」。风险：测试规模增长后 PR 反馈变慢——由观察项 O1 兜住 |
| A2 Vitest `--changed` + 兜底清单 | CI 按变更文件筛测试，共享层变更兜底全跑 | 收益约 10s/PR；风险：影响面清单与代码目录耦合、方向与兜底原则相反，漏测事故代价远大于 10s |
| A3 仅本地增量 | 开发者本地自用 related/changed，CI 全量 | 零 CI 风险；但本地全量同样仅十几秒，收益不显著 |

### 裁决 2：E2E 是否按模块裁剪

| 候选 | 方案 | 理由 / 风险 |
| --- | --- | --- |
| B1 登记观察项，暂不裁剪（**已裁定**） | 维持 E2E 全跑 | 冒烟规模下节省 20–40s 不抵映射规则维护（新增模块须同步过滤器，与代码目录耦合）；固定开销占大头。风险：E2E 增长后反馈线性变慢——由观察项 O2/O3 兜住 |
| B2 按模块裁剪 E2E | 扩展 ADR-0026 框架，per-module 过滤器按命中跑对应 spec | 收益 20–40s/单模块 PR；风险：映射维护 + 共享层判定遗漏致漏检 |
| B3 不裁用例，优化固定开销 | E2E webServer 复用前面 Build 产物，省二次构建 | 收益上限更高（约 1 分钟）；风险：改动在 Playwright 配置与构建产物传递，风险面大于收益 |
