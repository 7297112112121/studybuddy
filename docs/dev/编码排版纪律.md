# 编码排版纪律

涵盖 import 排版、注释风格与声明顺序规则——凡编写或修改产品代码的技能（dev_implementation 等）在每任务提交前逐条自查的裁判文档。本文件是编码排版规则的真源，规则**包括但不局限于**以下条目，新增排版规则登记于此。

## 可读性总则

- 代码的最终读者是人：AI 产出的代码必须以人类直接阅读理解为前提，可读性与正确性同等地位，编译通过、测试绿不构成可读性的豁免；
- 本文其余条目（命名、注释、声明顺序）都是这个前提的手段，不是独立目标；注释解释业务意图而非复述代码。

## import 排版

- **折行交由 Prettier 管理**（`.prettierrc.json`，行宽 80）：import 是否折行由能否塞进行宽决定，手工不再强制多行；保存时格式化与 CI 的 `npm run format:check` 门禁是唯一裁判；
- **分组与空行（手工维护，Prettier 只保留不改写）**：外部依赖（包名）之间隔一行，同包多条 import 不隔行；内部依赖（`@/`、相对路径）之间不隔行；外部与内部依赖之间隔一行；
- **排序（手工维护，Prettier 不排序 import）**：从上到下先外部依赖，后内部依赖。

```ts
// 合规格式示例
import { useState } from "react";

import { z } from "zod";

import { LoginForm } from "@/modules/auth/components/LoginForm";
```

## 注释风格

### 总则：非必要不注释

- **优先用清晰命名、拆分函数、精简结构实现自解释**，尽量减少注释；代码能自明的部分一律不写，注释是例外而不是标配；
- **禁止复述代码行为的废话注释**（不写「这一步遍历数组」「赋值给变量」这类）；
- 简单工具函数、CRUD、分支判断，默认不加行内注释；
- 输出代码时没有必须注释的点，就不强行加注释。

### 允许注释的场景

- **行内注释**仅限以下场景，且必须**简要**（一两句话内说清，禁止展开成段落或字段清单）：
  1. 业务特殊规则、产品隐含约束；
  2. 历史坑、已知 bug、临时 hack、后续要重构的标记；
  3. 算法思路、数学推导、非直观的复杂逻辑；
  4. 外部依赖限制、兼容性说明。
- **对外导出的公共函数/接口**：只保留简洁的 Doc 说明；**内部私有函数**若无特殊逻辑不写文档注释；
- 文件头需要时可由「作用 + 风险」两行简短构成；
- **禁止堆叠注释**：禁止成员清单、流程、延伸信息等字段式堆叠（旧「文件头字段规范」与「函数字段规范」即属此类，全部废止，也不再用「作用：」「风险：」等字段标签）；
- 注释简洁不啰嗦，代码本身优先可读；
- 合格示例：

```ts
/** 登录提交 */
```

### 禁止编号标记

- 所有注释（文件头、函数 JSDoc、行内注释）禁止出现编号标记（如 AXY-24、R2、D-13、Constraint 12、design 开放问题 #2）；编号是文档层的定位符，代码注释用自然语言把规则本身说清楚，出处由读者循文档地图查阅。
- 禁止以编号或计数指代规则（如「过滤五规则」「上述第 3 条」），需要提及规则时把规则内容完整写出。

### 术语中英并写

- 注释中引用代码实体（类型、类、函数、schema 等符号）与协议字面值（kind/verdict 取值如 NOT_FOUND、NEEDS_RANGE）时，一律先写中文术语，再括号补英文（如「条目提案（EntryProposal）」「未找到（NOT_FOUND）」），禁止单独裸写英文；
- 模块路径（@/…）不在并写范围。

## 防御

- **内部函数信任调用方**：参数非空、类型正确、状态合法由调用方与类型系统保证，内部不再重复判空；
- **不添加不必要的兜底分支**：类型系统与边界校验已排除的情形不再写防御代码；
- **优先可读性，防御逻辑最小化**：多一行防御不如少一行，发现冗余防御时随手删除。

### 命名

- 禁止无意义命名；除命名惯例（如 zod 的 `z`、drizzle 的 `tx` 与表回调 `t`、循环下标 `i`、排序比较器 `a`/`b`）或项目既有约定（如 `formatHhmm`、`MS_PER_DAY`）允许外，标识符一律用完整单词；
- 禁止缩写（如 `dow`、`y`/`m`/`d`、`h`/`m`、单字母回调参数）与中式英语。

### 声明顺序

- 从上到下：默认导出 → 具名导出 → 类型/常量 → 私有函数（不导出）沉底；
- 例外：`.tsx` 组件文件维持组件惯例——Props 类型在前、私有函数随后、默认导出组件殿后；`page.tsx` / `layout.tsx` 等路由文件维持 Next.js 惯例，默认导出留在文件末尾。

执行层说明：Prettier 不管注释，本约定与 import 分组/排序规则同待遇——由 dev_implementation 硬门禁逐条自查；存量文件不追溯整改，新写/被改到的文件按本约定执行。
