# 研发流程

研发流程分三大部分——产品设计、开发落地、测试提质——分别由 `.agents/skills/` 下的流程技能承载，技能间靠「引用上游已批准文档」强制接力。**总流程图与分支生命周期表的唯一真源在技能区 `.agents/skills/README.md`「总流程与分支生命周期」节（docs → skill 单向引用）；本文件只做面向人类的流程叙述，每个技能的触发条件、硬门禁、流程步骤与产出要求，以该技能目录下的 SKILL.md 为唯一真源，此处不复述。**

## 总流程

流程按三段单向推进：

1. **产品设计**：模糊想法 → 用户故事（产品批准门）→ 需求规范 proposal（批准门一）；产物落 `docs/product/AXY-<N>-<slug>/`，经 `docs/<slug>` 分支 PR 合并回 `master`；
2. **开发落地**：已批准 proposal → 架构设计 design（批准门二）→ 实现计划 → TDD 实现 → （可选，由用户显式决定）规范终审；产物落 `docs/dev/AXY-<N>-<slug>/` 与产品代码，经 `feat/AXY-<N>-<slug>` 分支 PR 合并回 `master`；
3. **测试提质**：验收各 proposal 的性能与质量要求（Q 条目），阶段技能暂缺。

两道批准门（proposal、design）未过，不得进入下一环节或写任何产品代码。技能间交接时下游默认只读的最小集，见技能区 `.agents/skills/README.md` 的「流程接力约定」。

**横切旁路**：已合并主分支的特性需要推翻重写、取代或废弃时，任意阶段可触发横切技能 `feature-supersede`——先定级（A 表述 / B AC / C 定位 / D 废弃）并重新批准，再代码处置（只 `revert` / `tag`，不改写主分支历史）、旧工件加墓碑，产出变更记录 `change-record.md`（第五份工件，dev_spec_review 判断「哪些代码是活的」的依据）。

### 分支生命周期

分支生命周期（两段式 `docs/<slug>` / `feat/AXY-<N>-<slug>` 的开启与收束时机及补充规则）的唯一真源在技能区 `.agents/skills/README.md`「总流程与分支生命周期」节，本页不再复制。

## 技能指针

| 部分 | 技能 | 一句话职责 |
| --- | --- | --- |
| 产品设计 | `product_design` | 模糊想法 → 用户故事（五大组成部分；编号未下发平铺 `docs/product/<feature>.md`，下发后迁入 `AXY-<N>-<slug>/story.md`，编号即路径，并登记总览） |
| 产品设计 | `product_proposal_writing` | 已批准用户故事 → 需求规范 proposal（批准门一；`docs/product/AXY-<N>-<slug>/`，含原型契约） |
| 开发落地 | `dev_architecture_design` | proposal → 架构设计 design（批准门二；与 ADR、代码目录约定核对） |
| 开发落地 | `dev_plan_writing` | design → 微任务实现计划（TDD 任务卡） |
| 开发落地 | `dev_implementation` | 已批准实现计划 → 逐任务 TDD 执行（产品代码 + 测试 + evidence 落盘；编码排版纪律在此承载） |
| 开发落地 | `dev_spec_review` | （可选，由用户显式决定是否触发）实现完成后对照 proposal 逐条终审，规范符合性与代码质量双重判定 |
| 横切 / 变更管理 | `feature-supersede` | 已合并主分支特性的推翻 / 取代 / 废弃：定级（A/B/C/D）→ 重新批准 → 代码处置（revert / tag）→ 墓碑 + 变更记录（第五份工件） |
| 测试提质 | （暂缺） | 验收各 proposal 的性能与质量要求（Q 条目），现阶段暂不编写 |

纯技术决策（选库、目录结构等）不走流程技能，改走 ADR 流程（docs/dev/adr/）。

每类文档的路径模式与全景（阶段 · 产物 · 产出技能 · 真源说明）见 [文档地图](./文档地图)。
