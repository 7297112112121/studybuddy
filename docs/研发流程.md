# 研发流程

研发流程分三大部分——产品设计、开发落地、测试提质——分别由 `.agents/skills/` 下的流程技能承载，技能间靠「引用上游已批准文档」强制接力。**本文件只做流程总览：每个技能的触发条件、硬门禁、流程步骤与产出要求，一律以该技能目录下的 SKILL.md 为唯一真源，此处不复述。**

## 总流程

```text
（master）
 ├─ docs/<slug> 分支（产品侧）
 │    模糊想法 → [product-design] → 用户故事（产品批准门）
 │              → [proposal-writing] → proposal（批准门一，产品侧） ── PR: docs → master
 └─ feat/AXY-<N>-<slug> 分支（开发侧）
      proposal → [architecture-design] → design（批准门二）
              → [plan-writing] → 实现计划
              → TDD 实现（含集成 / E2E 测试）
              → [spec-review] → 审查报告（性能与质量要求移交测试提质） ── PR: feat → master
```

两道批准门（proposal、design）未过，不得进入下一环节或写任何产品代码。技能间交接时下游默认只读的最小小节集，见 `.agents/skills/README.md` 的「流程接力约定」。

**横切旁路**：已合并主分支的特性需要推翻重写、取代或废弃时，任意阶段可触发横切技能 `feature-supersede`——先定级（A 表述 / B AC / C 定位 / D 废弃）并重新批准，再代码处置（只 `revert` / `tag`，不改写主分支历史）、旧工件加墓碑，产出变更记录 `change-record.md`（第五份工件，spec-review 判断「哪些代码是活的」的依据）。

### 分支生命周期（唯一真源）

流程与分支一一对应，两段式推进；**开分支与合并 PR 是流程动作，不是可选优化**。PR / squash merge / 分支清理等机械操作一律走 branch-wrapup 技能，此处不复述。

| 阶段 | 分支 | 承载内容 | 开启时机 | 收束时机 |
| --- | --- | --- | --- | --- |
| 产品设计 | `docs/<slug>` | docs/product 工件（story、proposal） | 创建或推翻用户故事时，从最新 `master` 开出（product-design / feature-supersede 产品侧开工时） | proposal 批准后，经 branch-wrapup PR 合并回 `master` |
| 开发落地 | `feat/AXY-<N>-<slug>` | docs/dev 工件（design / tasks / review）+ 产品代码 + 测试 | proposal 已合并进 `master`、进入 architecture-design 时，从最新 `master` 开出 | spec-review 通过后，经 branch-wrapup PR 合并回 `master` |

补充规则：

- docs 分支以特性 slug 命名——取号在分支上进行，编号下发后**不重命名分支**；feat 分支编号即路径，编号已由 proposal 承载；
- 实现期回流 proposal 追认、批准后的措辞级修订等小幅产品文档改动，随当前工作分支走，不单独开分支；
- feature-supersede 横切两侧分支：阶段 1–4（定级、冻结、story / proposal 重写与重新批准）与 `change-record.md` 落盘、product 侧墓碑走 docs 分支并 PR；阶段 5 代码处置与阶段 6 重走下游客、dev 侧（design / tasks / review）墓碑走 feat 分支并 PR。

## 技能指针

| 部分 | 技能 | 一句话职责 |
| --- | --- | --- |
| 产品设计 | `product-design` | 模糊想法 → 用户故事（五大组成部分；编号未下发平铺 `docs/product/<feature>.md`，下发后迁入 `AXY-<N>-<slug>/story.md`，编号即路径，并登记总览） |
| 产品设计 | `proposal-writing` | 已批准用户故事 → 需求规范 proposal（批准门一；`docs/product/AXY-<N>-<slug>/`，含原型契约） |
| 开发落地 | `architecture-design` | proposal → 架构设计 design（批准门二；与 ADR、代码目录约定核对） |
| 开发落地 | `plan-writing` | design → 微任务实现计划（TDD 任务卡） |
| 开发落地 | `spec-review` | 实现完成后对照 proposal 逐条终审，规范符合性与代码质量双重判定 |
| 横切 / 变更管理 | `feature-supersede` | 已合并主分支特性的推翻 / 取代 / 废弃：定级（A/B/C/D）→ 重新批准 → 代码处置（revert / tag）→ 墓碑 + 变更记录（第五份工件） |
| 测试提质 | （暂缺） | 验收各 proposal 的性能与质量要求（Q 条目），现阶段暂不编写 |

纯技术决策（选库、目录结构等）不走流程技能，改走 ADR 流程（docs/dev/adr/）。

每类文档的路径模式与全景（阶段 · 产物 · 产出技能 · 真源说明）见 [文档地图](./文档地图)。
